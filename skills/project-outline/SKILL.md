# 项目大纲

从已有代码逆向生成「项目大纲」，让项目维护者无需通读源码即可了解项目功能全貌。

本 skill 从已有代码反推项目功能全貌，只产人读文档，不生成代码。本 skill 只做一次性全量生成，不做定时或增量更新（无文件 watch、无 commit-diff 增量同步）。

## 产物

| 产物 | 路径 | 说明 |
|---|---|---|
| 项目大纲 | `docs/project-outline.md` | 人读主产物 |
| 全量明细附录（大型项目，可选） | `docs/project-outline-coverage.md` | 大清单的完整入口/实体明细；正文只留分组摘要，全量入此 |

默认只产出 Markdown。章节结构、写作风格、读写规则、覆盖率核对小节格式见 `references/outline-structure.md`。

| 逆向提取实体/功能/流程/规则的方法、调用链追踪、噪音过滤、推断项标注、覆盖率核对方法 | `references/reverse-extraction-methodology.md` |

## 工作流程

### 1. 探测项目类型、技术栈与规模

- 读取构建文件、配置文件、目录结构，判断语言/框架/项目类型；按需读取 `references/tech-detection-guide.md`。
- 同时判定项目规模（小/中/大）：按源码文件数与入口点枚举数判定（阈值见 `references/tech-detection-guide.md`）。大型项目必须走分区并行遍历（见步骤 2 与 `references/large-project-traversal.md`）。
- 记录到项目大纲 §2 架构与技术栈。

### 2. 全量枚举入口、模块与实体（覆盖率的根）

- 用**确定性 grep 信号**全量枚举，不靠逐文件阅读"注意到"：所有对外入口（Controller/Router/Resolver/IPC/CLI/Job/MQ）、所有顶层模块/包、所有数据模型（ORM 模型/实体类/DDL 表）。各栈枚举信号见 `references/tech-detection-guide.md`。
- 产出原始枚举清单作为后续归类与覆盖率核对的基线——这是"广撒网"步骤，目标是**穷举不漏**，而非此时就理解每个项。
- **大型项目**：按顶层模块/目录分区，派发并行子代理逐区枚举（每区产出一个分片清单），再合并去重；分区与子代理模板见 `references/large-project-traversal.md`。单代理无法在上下文内装下大库，不分区并行就必然漏功能。
- 枚举清单是工作基线，不直接铺进正文，但保留为覆盖率核对的依据（见步骤 8）。
- **全仓扫描，禁止采样**：枚举必须覆盖整棵源码树（仅排除默认排除 glob，见 `references/tech-detection-guide.md`），不得只扫已打开文件/部分目录/主模块——只扫部分是功能不全的根因。

### 3. 扫描模块与目录结构

- 基于枚举结果识别顶层模块/包/分层与目录组织约定（如 API/Biz/Service/Repository 或 routes/services/models）。
- 记录到 §3 模块结构（含模块间依赖与跨模块调用边，即 L4 边集）。

### 4. 逆向提取数据模型与关系

- 基于枚举的实体清单，从 ORM 模型/实体类/PO/DDL 提取核心业务对象与关系；过滤纯技术实体（排除项记入覆盖率核对）。
- 记录到 §4 数据模型。

### 5. 逆向提取功能清单与入口（逐项归类，防漏重点）

- 对步骤 2 枚举的**每个入口点逐项归类**：命名业务功能、归属模块、入口位置（`文件:方法`）、类型（api/ipc/cli/job/mq）。
- 按 `references/reverse-extraction-methodology.md` 的「§5 逐项生成协议」执行：把入口基线当 checklist，先排噪音、逐项归类（一行对一条，不得合并吞并）、按业务模块分组、对账（§5 行数 + 排除数 = 入口基线数）、最小内容校验重扫。
- 枚举的入口必须 100% 归类，或显式标注为噪音排除（如健康检查/actuator）；无法归类的进 §9，不得静默丢弃。
- 记录到 §5 功能与接口（含入口）。

### 6. 逆向提取关键流程与规则

- 从编排层（Biz/usecase）追踪端到端调用链，提炼核心流程；从计算/校验逻辑提取业务规则。
- 只保留高价值，过滤基础校验噪音。
- 记录到 §6 核心流程 + §7 业务规则。

### 7. 汇总外部依赖与维护指南

- 从配置/DI 提取 DB/MQ/外部服务依赖；编写「想改 X 去哪里」维护指南。
- 记录到 §2 架构与技术栈（外部依赖）+ §8 维护指南。

### 8. 覆盖率核对与汇报

- 对照步骤 2 的枚举基线，逐维度核对并写入项目大纲「覆盖率核对」小节（格式见 `references/outline-structure.md`）：枚举总数 / 已归档 / 排除(噪音) / 待确认。
- **枚举项未 100% 归位不得准出**——这是解决"大型项目只有部分功能"的硬门禁。
- 跑「扫描完整性自检」（见 `references/reverse-extraction-methodology.md`）：双信号交叉计数、跨切面总数核对、每模块非空校验——防止只扫了部分项目。
- 运行 `validate_project_outline.py`；把推断项汇总到 §9 待确认项，供维护者校验。
- 向用户汇报产物路径、覆盖率与统计。

各维度的具体提取启发式、调用链追踪方法、噪音过滤清单、推断标注规则与覆盖率核对方法见 `references/reverse-extraction-methodology.md`。

## 逆向提取重点

基于代码反推，但不要机械罗列全部文件。判断并聚焦：

- 真正的数据模型（剔除审计基类、日志表、纯技术中间表）
- 对外暴露的功能入口（剔除内部 helper、工具方法）
- 端到端业务流程（剔除单步 CRUD、纯数据搬运）
- 影响计算/流程/一致性的高价值规则（剔除字段必填、枚举范围等基础校验）
- 模块边界与依赖方向（剔除循环依赖噪音，但要在 §9 标注发现的坏味道）

「聚焦」发生在**归类与撰写**阶段，不在**枚举**阶段——枚举必须穷举，归类时再决定哪些入正文、哪些标噪音排除，且排除项要可追溯。

## 推断项标注

逆向必然有推断。凡非直接由代码注释/声明确证、而是由命名/调用链推断的结论，必须标注 `(推断)` 并写入 §9 待确认项，让维护者知道哪些需要校验；把握很大但未经注释确证的标注 `(高置信推断)`。详细判定规则见 `references/reverse-extraction-methodology.md`。

## 写作要求（人读优先）

项目大纲是给维护者读的，不是代码清单 dump。枚举基线保证不漏，但正文必须人能看懂——这两件事不矛盾：枚举保「不漏」，写作保「能读」。

- **业务语言优先**：功能用业务名（「创建燃气合同」），代码位置（`GasContractController.createGasContract()`）作引用放括号或链接，不作主体。
- **分组+叙述，不铺平表**：几十个入口平铺成一张表没人能读；按业务模块/子域分组，每组先 1–3 句白话说明这组干什么，再跟一张紧凑表（功能名/说明/入口）。
- **导读先行**：§1 用一段话讲清「系统是什么、解决什么问题、核心能力」，让读者先建立整体认知再看细节。
- **重点项入正文，全量明细入附录**：大清单（如 >20 个入口/实体）的完整明细放 `docs/project-outline-coverage.md`，正文只留分组摘要与高频/核心项。
- **流程用业务步骤叙述**：§6 按业务步骤编号白话叙述（创建→审批→生效），方法签名作括号引用，不贴调用链原始序列。
- **规则给口径不给代码**：§7 一句话讲清公式/约束（「利润=交付量×(售价−采购价)」），代码位置作引用。
- **不贴技术噪音**：正文不出现 grep 正则、完整 SQL DDL、参数类型签名、import 清单、构建脚本。

各章节的人读格式与正反例见 `references/outline-structure.md`。

## 准出门禁

项目大纲完成后完成以下检查：

1. `docs/project-outline.md` 含全部必选章节（§1–§8）与「覆盖率核对」小节（有推断时还含 §9），无 TBD/TODO/占位符。
2. **覆盖率门禁**：步骤 2 枚举基线逐维度 100% 归位——每个枚举的入口/模块/实体要么已归档到对应章节，要么在「覆盖率核对」中显式标注为噪音排除；不得静默丢弃。未达 100% 不得准出。
3. **§5 功能与接口逐项对账**：§5 行数 + 噪音排除数 = 入口枚举基线数；每个顶层模块非空（有功能或显式标"无对外功能"）。
4. 每个识别出的数据模型、对外功能都有归属章节与入口位置。
5. §8 维护指南覆盖「最常改的 N 类功能」到文件路径的映射。
6. §9 待确认项列出全部 `(推断)` / `(高置信推断)` 项。
7. 运行 `validate_project_outline.py` 通过（无 FAIL）。

最终向用户汇报：

```text
项目大纲已生成：docs/project-outline.md。
覆盖率核对：入口 N/N、模块 N/N、实体 N/N 已归档或显式排除（见「覆盖率核对」小节）。
覆盖：模块 N 个、数据模型 N 个、对外功能 N 个、关键流程 N 条、关键规则 N 条。
推断项：N 项待确认（见 §9）。
请维护者重点核对 §9 推断项与未归档项。
```

## 可视化伴侣

如果项目大纲明显涉及架构图、模块依赖图或实体关系图，可以单独询问用户是否需要可视化伴侣。该询问必须单独成句，不与澄清问题混在一起。用户拒绝时，继续以文本输出项目大纲。

## 关键原则

- 代码为唯一事实源，文档为派生视图。
- 全量枚举保覆盖：先穷举入口/模块/实体再归类，不靠单次阅读采样；大型项目分区并行遍历，覆盖率未达 100% 不准出。
- 人读优先：枚举保不漏、正文写给人看——业务语言、分组叙述、全量明细入附录。
- 聚焦业务全貌，不机械罗列文件。
- 推断必须显式标注，让维护者可校验。
- 按业务子域拆分，禁止按 MVC/技术层拆分；分层递进理解（L2 树→L3 模块→L4 边→L5 功能），见 `references/reverse-extraction-methodology.md`。
- 保持 skill 主文件短小，细则放 references。
