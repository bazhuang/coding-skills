# 逆向提取方法论

本文件定义从已有代码反推业务全貌的提取启发式、调用链追踪方法、噪音过滤清单与推断标注规则。执行工作流程各步骤时按需读取。

## 通用原则

1. **代码为唯一事实源**：结论必须能在代码中找到证据（文件/类/方法/配置）。无法在代码中定位的，标 `(推断)` 并说明依据。
2. **聚焦业务，不罗列文件**：项目大纲给维护者看功能全貌，不是目录树 dump。每个维度都先判断「这是业务还是技术噪音」。
3. **宁可少而准，不要多而杂**：拿不准是否高价值的，先放进 §9 待确认，不直接塞进 §6/§7。
4. **置信度分层**：注释/声明/配置直接确证 = 事实；命名/调用链强推断 = `(高置信推断)`；靠惯例猜测 = `(推断)`。
5. **全量枚举优先**：每个维度先穷举再归类——用确定性 grep 信号枚举全部入口/模块/实体产出基线清单，再逐项判断业务归属。绝不靠单次阅读"注意到什么写什么"，那是大型项目漏功能的根因。大型项目按 `references/large-project-traversal.md` 分区并行枚举。
6. **按业务子域拆分，禁止按 MVC/技术层拆分**：模块/功能清单按业务子域（如「合同」「结算」「库存」）划分，不要按 controller/service/model 或 routes/services/models 这类技术分层划分——技术分层是同一功能的切面，按它拆会让一个功能散落多章，维护者看不出功能全貌。
7. **分层递进理解**：先结构后细节，按 L2 目录树 → L3 模块职责 → L4 模块间边/数据流 → L5 功能与流程 逐层深化，每层输出喂给下一层；不要一上来就钻进单文件。详见下文「分层理解」。

## 各维度提取启发式

### 模块与目录结构（→ §3 模块结构）

- 从顶层目录/包名识别模块边界，按分层约定归类（API/Biz/Service/Repository 或 routes/services/models）。
- 从 import/依赖注入方向判断模块间依赖，绘制依赖方向；并追跨模块调用边（L4 边集：谁调谁、同步/异步、主数据流向），供 §3 依赖图与 §6 流程。
- 多模块项目（Maven 多模块 / monorepo）按子项目划分模块。
- **噪音**：工具包、配置包、常量包不作为业务模块，归入技术栈说明。

### 数据模型与关系（→ §4 数据模型）

- 提取来源优先级：ORM 模型注解 > 实体/PO 类 > DDL `CREATE TABLE` > DTO/VO（DTO/VO 不一定是实体，仅作线索）。
- 关系来源：外键、`@OneToMany`/`relationship()` 等关联注解、 join 查询。
- 每个实体记录：名称、对应表名、关键字段、与谁有关系。
- **噪音过滤**：审计基类（BaseEntity）、日志表、操作记录表、纯技术中间表（如 flyway/alembic 迁移表）、字典表（归入主数据说明）。

### 功能清单与入口（→ §5 功能与接口，含入口列）

- 提取来源：`@RestController`/`@GetMapping`、APIRouter 路由、GraphQL resolver、Electron IPC handler、CLI command、定时任务 `@Scheduled`/cron、MQ consumer。
- 按模块分组，每个功能标注：功能名、入口位置（`文件:方法` 或 `类.方法()`）、类型（api/ipc/cli/job/mq）。
- 功能名用业务语言（「创建燃气合同」），不要用方法名直译。
- **噪音过滤**：内部 helper、纯工具方法、健康检查/actuator 端点（归入技术栈说明）、仅给前端用的元数据接口。

### 核心流程（→ §6 核心流程）

- 从编排层（Biz/usecase/application service）入手，追踪端到端调用链，提炼跨多步的业务路径（如创建→审批→生效→结算）。
- 流程选取标准：跨 ≥2 个对象、跨 ≥2 个方法、有状态流转或事务边界。单步 CRUD 不算流程。
- 每条流程记录：名称、关键步骤序列（方法名）、涉及实体、状态变化。
- 调用链追踪方法见下文。

### 业务规则（→ §7 业务规则）

- 只提取高价值规则：业务计算公式、跨实体约束、跨实体一致性、影响流程分支或算法优先级的领域决策。
- 每条规则记录：名称、代码位置、一句话口径（如「利润 = 交付量 × (售价 − 采购价)」）。
- **噪音过滤**：字段必填、正数校验、枚举范围、标准外键存在性等基础校验一律不入 §7。

### 外部依赖（→ §2 架构与技术栈）

- 来源：数据源配置（application.properties/yml、datasource）、DI 注入的外部 client、消息队列配置、对象存储配置、第三方 SDK 依赖。
- 每项记录：类型（database/mq/storage/external-service）、名称、用途。

## 分层理解（L2–L5）

借鉴代码理解引擎的分层做法，按层递进，每层只做一件事，上一层输出约束下一层：

| 层 | 产出 | 做什么 | 喂给下一层 |
|---|---|---|---|
| L2 目录树 | 顶层目录/包结构 + 排除噪音后的源码树 | `tree`/`glob` 扫目录，套用默认排除 glob（见 `tech-detection-guide.md`） | 模块边界候选 |
| L3 模块职责 | 每个业务子域模块的 1–2 句「知识卡」：边界、职责、约定 | 按 §3 启发式 + 每模块 Focus-on（见下）定位关键文件，读 README/入口/实体 | 模块清单与职责 |
| L4 模块边/数据流 | 模块间依赖方向 + 跨模块调用边 + 主数据流 | 从 import/DI/编排层追跨模块调用，标方向 | 边集，供 §3 依赖图与 §6 流程 |
| L5 功能与流程 | 入口→编排→持久化的调用链 | 在模块内追调用链（见「调用链追踪方法」） | §5/§6/§7 |

- 每层设「这层做完了吗」的自检（如 L3 每个模块都有职责句才算完），未完不进下一层。
- L4 的「边」是大型项目最易漏的维度——单看模块看不出谁调谁，必须显式追跨模块调用与数据流。
- 分层不是阶段门禁，是提取顺序：可一气呵成走完 L2→L5，但顺序不能跳。

## 每模块 Focus-on 文件聚焦

进 L3/L5 深挖某个模块时，不要全目录扫，先按 concern 用 glob 收窄到相关文件，再读。这是搜索效率的关键：

| Concern | 聚焦 glob/关键词 |
|---|---|
| 配置 | `config/`、`*.yaml`、`*.toml`、`*.env*`、`application.properties`、启动配置加载 |
| 错误处理 | `errors/`、error 类型、错误码定义、panic/recover、中间件错误处理 |
| 构建发布 | `Makefile`、`build*.sh`、`Dockerfile`、CI 配置、版本号策略 |
| 依赖管理 | `go.mod`/`go.sum`、`package.json`、vendor 策略、私有 registry |
| 日志 | `log/`、`logging/`、logger 初始化、结构化字段、日志级别 |
| UI/前端 | `*.css`、`*.scss`、`tailwind.config.*`、主题文件、组件库、design tokens |
| 鉴权 | `auth/`、`middleware/`、token/session、RBAC、OAuth flow |
| 数据访问 | `repository/`、`dal/`、`mapper`、ORM 模型、migration |

- 先 `grep --glob '<pattern>' --type '<lang>'` 收窄，再 `read_file` 精读，避免把时间花在无关文件上。
- 一个模块通常命中 1–3 个 concern；命不中的 concern 跳过。

## 双轨搜索：grep 枚举 + 语义检索

两类搜索各有不可替代的作用，配合用：

- **grep 枚举（确定性）**：用于「全量列清单」——所有入口、所有实体、所有 `@Scheduled`。保证不漏，是覆盖率核对的基线。用 ripgrep `--glob`/`--type` + 默认排除清单。
- **语义检索（概念性）**：用于「这个概念在哪」——如「利润计算」「审批流」「限流」。若运行环境有 codebase 语义检索/向量检索工具（如 `search_codebase`/symbol search），优先用它定位概念起点，再用 grep 在该区域穷举。
- 无语义检索工具时，降级为「grep 关键词（中英文业务术语 + 同义词）→ 命中文件 → read」，并标注检索范围有限。
- 顺序建议：语义检索定位 → grep 在定位区域穷举 → read 精读证据。避免「逐文件 read 碰运气」。

## 调用链追踪方法

从对外入口追到持久化，是提炼 §5/§6/§7 的核心手段：

1. **入口**：定位 Controller/Router/IPC handler 方法（见 tech-detection-guide）。
2. **编排**：入口通常调用一个 Biz/usecase 方法，这是业务编排层——流程的骨架在这里。
3. **服务**：Biz 调用 Service 方法，业务逻辑与计算在此。
4. **持久化**：Service 调用 Repository/Mapper/DAO，落到表。
5. **跨链**：注意一个 Biz 方法调用多个 Service（跨对象编排），这往往是关键流程的标志。

追踪时记录方法签名链，作为流程步骤与维护指南的依据。遇到反射/动态分发/消息驱动无法静态追全的，标注 `(推断)` 并说明追到哪一层断掉。

## 噪音过滤清单

以下内容不入业务维度，按括号归属处理：

| 噪音 | 处理 |
|---|---|
| 审计基类、BaseEntity、create_by/gmt_create 等审计字段 | §2 技术栈说明一句带过 |
| 日志表、操作记录表、迁移表 | 不入 §4 |
| 工具类、常量类、配置类 | 不入 §3 业务模块 |
| 健康检查、actuator、metrics 端点 | 不入 §5 |
| 字段必填、正数、枚举范围校验 | 不入 §7 |
| 单步 CRUD、纯数据搬运 | 不入 §6 |
| 框架生成的样板代码 | 不入任何业务维度 |

发现坏味道（循环依赖、超长方法、跨层调用、SQL 拼接）不入业务维度，但记入 §9 待确认项提示维护者。

## 覆盖率核对方法

逆向提取的最大风险是"只写了注意到的部分"。用枚举基线做逐维度核对，把"漏没漏"变成可量化门禁：

1. 步骤 2 产出的枚举基线 = 每个维度"应该有的总数"。
2. 提取完成后，逐维度统计：枚举总数 / 已归档到对应章节 / 显式排除(噪音) / 待确认(归属未定)。
3. 覆盖率 = (已归档 + 排除) / 枚举总数，必须 100%。
4. 未归档且未排除的项 = 漏项，必须补提取或显式标噪音排除，不得静默丢弃。
5. 核对结果写入项目大纲「覆盖率核对」小节（格式见 `outline-structure.md`）。

各维度枚举信号见 `tech-detection-guide.md`；大型项目分区枚举的合并去重见 `large-project-traversal.md`。

## §5 功能与接口：逐项生成协议（防漏）

§5 功能最散、最易漏。按「逐项 tick」协议执行，把"写多少算多少"变成"每个枚举入口都有交代"：

1. **基线当清单**：把步骤 2 的入口枚举基线作为 §5 待办 checklist，每条入口 = 一行待办。
2. **先排噪音**：从清单剔除噪音入口（健康检查/actuator/内部 helper/纯元数据接口），剔除项记入覆盖率核对「排除」列并备注类别——不静默删。
3. **逐项归类**：对剩余每条入口产出一行——功能名（业务语言）/ 模块 / 入口位置（`文件:方法`）/ 类型(api/ipc/cli/job/mq)。一行对一条，不得合并吞并。
4. **按业务模块分组**：行按业务子域分组（不按技术层），每组先 1–3 句叙述模块能力，再跟紧凑表。
5. **对账（硬门禁）**：§5 行数 + 排除数 = 入口基线数。不等即有漏项，补归或补排，不留缺口。
6. **最小内容校验 + 重扫**（借鉴 Qoder 的 min-length+retry）：非空模块却 0 条功能 → 重扫该模块（套用每模块 Focus-on + 双轨搜索），直到对得上或确认无对外功能。
7. **无法归类项**：入口存在但归属/含义不明 → 进 §9 待确认项，标注入口位置与卡点，不丢弃。

## 扫描完整性自检（防只扫部分项目）

借鉴 Qoder（对内容不足 retry、对失败 catalog 标 FAILED 而非跳过、跨切面边界核对），用多重独立核对防止"只扫了部分代码就开写"导致功能不全：

| 自检项 | 做法 | 不通过则 |
|---|---|---|
| 全仓 vs 已扫 | 枚举基线覆盖的文件数 vs 全仓源码文件数（减默认排除） | 缺口大 → 补扫缺的目录 |
| 双信号交叉计数 | 用两个独立 grep 信号各计一次入口数（如 `@RestController` 与 `@.*Mapping`）比对 | 不等 → 定位差集补齐 |
| 跨切面总数核对 | 全仓跨切面 grep 入口总数 = 各分区/各模块之和 | 不等 → 漏或重，定位补齐 |
| 每模块非空 | 每个顶层模块至少 1 条功能或显式标"无对外功能" | 空模块 → 重扫该模块 |
| §5 对账 | §5 行数 + 排除数 = 入口基线数 | 不等 → 补归/补排 |
| 失败项不吞 | 无法归类的入口进 §9，不静默丢 | 有静默丢 → 回填 §9 |

- 在步骤 8 统一跑一遍；大型项目在合并基线后跑（见 `large-project-traversal.md` 的防漏自检）。
- 关键原则：**宁可多扫一遍，不可凭"差不多"开写**——每一项的去向都要显式可追溯。

## 推断项标注规则

| 标注 | 判定 | 示例 |
|---|---|---|
| 无标注（事实） | 代码注释/声明/配置直接确证 | `@TableName("gas_contract")` → 实体对应表 gas_contract |
| `(高置信推断)` | 命名/调用链强推断，几乎无歧义 | 方法名 `calculateProfit` + 公式代码 → 利润计算规则 |
| `(推断)` | 靠惯例/部分线索猜测，有歧义 | 多个 service 调用顺序 → 推断为审批流节点顺序 |

标注要求：

- 在 Markdown 正文行末标 `(推断)` / `(高置信推断)`。
- §9 待确认项逐条列出：推断项、依据、置信度、建议维护者如何校验（看哪个文件/问谁）。
- 高置信推断也要进 §9——「高置信」不等于「已确证」，仍需维护者过目。
- 项目大纲交付时明确告知用户 §9 的项数，引导优先核对低置信项。
