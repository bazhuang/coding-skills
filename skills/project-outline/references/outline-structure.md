# 项目大纲结构与读写规则

本文件定义 `docs/project-outline.md` 的章节结构、写作风格、维护指南格式与读写规则。生成、增量更新、交接时读取。

## 章节结构

项目大纲按以下章节组织。§1–§8 必选；§9 待确认项在存在推断项时必选；另含「覆盖率核对」小节。入口信息并入 §5、外部依赖并入 §2，不再单列。

| 章节 | 内容说明 | 必选 |
|---|---|---|
| §1 项目概览 | 系统是什么、解决什么业务问题、业务域边界 | 是 |
| §2 架构与技术栈 | 语言/框架/分层/部署形态、关键依赖版本、外部依赖（DB/MQ/外部服务/存储） | 是 |
| §3 模块结构 | 顶层模块/包、各模块职责、模块间依赖与跨模块调用边（L4 边集） | 是 |
| §4 数据模型 | 核心领域对象、关键字段、实体间关系 | 是 |
| §5 功能与接口 | 对外功能按模块分组，紧凑表含入口列；必须覆盖入口枚举基线 100%（每条入口一行或显式噪音排除） | 是 |
| §6 核心流程 | 端到端业务路径（创建/审批/计算/结算等），按调用链提炼 | 是 |
| §7 业务规则 | 计算公式、跨实体约束、影响流程分支的领域决策 | 是 |
| §8 维护指南 | 「想改 X 功能去哪个文件」速查表 | 是 |
| §9 待确认项 | 全部 `(推断)` / `(高置信推断)` 项汇总 | 有推断时必选 |

**按项目规模裁剪**：小项目可将 §4 数据模型与 §5 功能清单合并叙述、§9 推断项少时并入覆盖率核对小节；大项目可把 §5 按子域拆为多个子章节。合并/拆分后章节关键词仍须保留，供 `validate_project_outline.py` 识别。

## 写作风格

项目大纲面向维护者人读，不是机器 inventory。总原则：

- **业务语言，代码作引用**：主体用业务名词与白话；类名/方法名/路径只作定位引用，放括号或作链接，不替代叙述。
- **先叙述后表格**：每个章节先用 1–3 句话讲「这部分是什么、为什么」，再给表格/清单。表格是细节补充，不是正文本身。
- **分组而非平铺**：超过 ~8 项的清单必须按业务模块/子域分组，每组带短叙述；禁止把几十行平铺成一张裸表。
- **摘要入正文，全量入附录**：大清单的完整明细（全部入口/全部实体字段）放 `docs/project-outline-coverage.md`，正文只留分组摘要与核心项。
- **不贴技术噪音**：正文不出现 grep 正则、完整 SQL DDL、参数类型签名、import 清单、构建脚本。

## 各章节人读格式

| 章节 | 人读写法 | 避免 |
|---|---|---|
| §1 项目概览 | 一段话：系统是什么、解决什么业务问题、核心能力、边界；配「一句话定位」 | 直接贴目录树或技术栈清单 |
| §2 架构与技术栈 | 语言/框架/分层 + 外部依赖小节（DB/MQ/外部服务）；关键版本 | 平铺全部依赖清单 |
| §3 模块结构 | 按模块分组，每个模块 1–2 句职责 + 模块间依赖/跨模块调用边；可用依赖示意图 | 平铺全部包名 |
| §4 数据模型 | 按业务域分组，每个实体一句话说明 + 关键字段（≤5 个）+ 关系；全字段表入附录 | 贴完整 PO 字段/类型表 |
| §5 功能与接口 | 按模块分组，每组短叙述 + 紧凑表（功能名/说明/入口）；每条枚举入口一行或显式噪音排除，禁止只写注意到的；>20 项时正文留核心，全量入附录 | 平铺几十行路由表 |
| §6 核心流程 | 业务步骤编号叙述（创建→审批→生效），方法签名作括号引用 | 贴调用链方法序列 |
| §7 业务规则 | 一句话口径（公式/约束）+ 代码位置引用 | 贴原始校验代码 |

§5 一组的正例：

```markdown
### 合同管理

提供燃气合同的创建、审批、结算等全生命周期能力。

| 功能 | 说明 | 入口 |
|---|---|---|
| 创建合同 | 录入合同基础信息，状态置为草稿 | `GasContractController.createGasContract()` |
| 审批流 | 多级审批，通过后合同生效 | `GasContractBizService.executeApprovalFlow()` |
```

反例（避免）：把 87 个 `@PostMapping` 路径平铺成一张四列表（method/path/handler/params），无分组、无叙述。

## 附录与完整清单

当某维度枚举数较大（入口 >20、实体 >15、或需要全字段）时：

- 正文保留**分组摘要 + 核心项**（高频、跨模块、业务关键）。
- **完整明细**写入 `docs/project-outline-coverage.md`（可选附录），按维度分组列出全部项与去向，供需要时查阅。
- 覆盖率核对仍以全量枚举为分母——附录存全量、正文给摘要，两者不矛盾：附录保「不漏」，正文保「能读」。

## 覆盖率核对小节

项目大纲正文末尾（§9 之后或之前均可）必须含「覆盖率核对」小节，记录枚举基线的逐维度归位情况——这是防止"大型项目只写出部分功能"的硬门禁的可视化：

```markdown
### 覆盖率核对

| 维度 | 枚举总数 | 已归档 | 排除(噪音) | 待确认 | 覆盖率 |
|---|---|---|---|---|---|
| 入口点 | 87 | 82 | 5 | 0 | 100% |
| 顶层模块 | 12 | 12 | 0 | 0 | 100% |
| 数据模型 | 34 | 31 | 3 | 0 | 100% |
```

- 覆盖率 = (已归档 + 排除) / 枚举总数，必须达 100%。
- 「排除(噪音)」需在表下备注排除项类别与数量（如：健康检查 3、actuator 2），让维护者知道丢掉了什么、为何丢。
- 「待确认」对应 §9 中归属未定的推断项。
- 枚举总数来自步骤 2 的全量枚举基线；大型项目来自分区合并后的全局基线（见 `references/large-project-traversal.md`）。
- 大型项目建议同步保留分片枚举清单为 `docs/project-outline-coverage.md`（可选），逐项记录每个枚举入口/实体的去向，便于审计。

## 维护指南格式

§8 以速查表形式给出「最常改的 N 类功能 → 代码位置」映射，让维护者按改动意图直接定位文件：

```markdown
| 想改什么 | 去哪里 | 备注 |
|---|---|---|
| 合同创建逻辑 | `app/biz/gas_contract_biz.py:create_gas_contract` | 调 GasContractService.insert |
| 合同审批流 | `GasContractBizService.executeApprovalFlow()` | 事务在此层 |
| 利润计算口径 | `GasContractService.calculateProfit()` | 见 §7 利润公式 |
```

- 「去哪里」尽量精确到 `文件路径:方法` 或 `全限定类名.方法()`，可点击。
- 备注指向相关章节或上下游方法，帮助维护者顺藤摸瓜。
- 覆盖高频改动点即可，不必穷举全部方法。

## Markdown 读写规则

1. **生成前**：检查 `docs/project-outline.md` 是否已存在。
   - 存在：读取现有内容作为基线，告知用户「已加载上次项目大纲」，按增量合并而非整体推翻（除非用户要求重做）。
   - 不存在：从零生成。
2. **每次更新**：覆盖写入完整当前版本（非增量片段），确保文件可被其他 agent 直接接手。
3. **格式**：普通 Markdown，不写入平台专用 `<artifact>`/card/HTML 标记；这些标记仅作展示，不作为事实源。
4. **代码位置引用**：使用 `文件路径:方法` 或 `全限定类名.方法()` 形式，便于点击跳转。
5. **推断标注**：凡推断结论在行末标 `(推断)` 或 `(高置信推断)`，并在 §9 汇总。
6. **跨会话延续**：用户说「继续上次的项目大纲」时，读取文件从中断处继续。
