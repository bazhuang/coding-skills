# 阶段1：模块合成

从已有代码全量提取模块知识，产出模块树作为目录规划与覆盖率核对的基线。

> 设计原则：先建仓库清单再写文档（inventory 优先）；模块树用「路径 + 业务描述 + 后代规模提示」三段式，路径作为稳定标识符；逐模块知识字段固定为 9 项，其中 `architecture_design` 是后续文章正文的主信号。agent 本体用原生文件工具直接完成全流程，不引入独立运行时或状态机。

## 步骤

### 1. 全量枚举源码树（覆盖率的根）

- 用**确定性 grep/glob 信号**全量枚举，不靠逐文件阅读"注意到"。覆盖整棵源码树，仅排除默认 glob：

  ```
  .git/ node_modules/ dist/ build/ .next/ out/ target/ venv/ .venv/
  __pycache__/ *.pyc .idea/ .vscode/ coverage/ .cache/ tmp/
  ```

- **禁止采样**：不得只扫已打开文件/部分目录/主模块——只扫部分是功能不全的根因。大型项目必须走分区并行遍历（见下）。
- 枚举信号按技术栈（确定性信号，不靠逐文件阅读"注意到"）：
  - 构建文件：package.json / pom.xml / go.mod / Cargo.toml / build.gradle / pyproject.toml / requirements.txt
  - 入口点：Controller / Router / Resolver / main / CLI / Job / MQ handler
  - 数据模型：ORM 模型 / 实体类 / DDL / schema 定义
  - 配置：.env.example / config / docker-compose / Makefile

### 2. 构建模块树

基于枚举结果识别顶层模块/包/分层与目录组织约定，构建树状视图。每节点：

```
<tree-prefix>`<path>` — _<业务描述>_[ [N 子模块]]
```

- **path**：斜杠分隔，ASCII，与 read_file 路径同形；root 为 `/`。这是模块的稳定标识符。
- **描述**：一句话说明模块的**业务功能**——这个模块做什么（提供什么能力、解决什么问题），而不是"这个目录在哪"。从代码反推，不臆造。
- **`[N 子模块]`**：非叶节点的后代计数——规模提示，标识父模块；父模块生成时其 `## 架构设计` 可综合子模块职责分工。

示例：

```
/ — _燃气智能体平台_[ [4 子模块]]
├── skills/ — _可插拔 AI 技能集合（本体建模/代码生成/项目概览/知识库）_[ [6 子模块]]
│   ├── ontology-modeling/ — _燃气业务本体建模，管理实体、关系与术语库定义_
│   ├── code-generation/ — _根据需求自动生成业务代码_
│   └── code-verification/ — _生成代码的自动化验证与质量检查_
│   └── ...
├── docs/ — _项目文档与规范_
├── .claude/ — _Claude IDE 配置与 settings_
└── manifest.json — _平台入口：技能清单、路由、依赖声明_
```

> 描述聚焦"能力"而非"位置"：`ontology-modeling/` 的描述是"燃气业务本体建模，管理实体、关系与术语库定义"而不是"本体建模模块目录"。

### 3. 逐模块提取知识

对模块树中**每个模块**提取以下字段：

| 字段 | 说明 | 提取方法 |
|---|---|---|
| `description` | 模块的业务能力概述（1-2 句），聚焦功能定位 | 读入口文件/README/目录结构反推 |
| `architecture_design` | **主信号**——架构设计、分层、关键抽象、设计意图 | 从编排层/核心类反推；后续文章生成时直接改写入正文，不重新推导 |
| `tech_stack` | 使用的技术栈/框架/库 | 从依赖文件 + import 反推 |
| `coding_conventions` | 编码约定（命名/模式/测试标准） | 从代码风格反推 |
| `unique_setup` | 特殊配置/安装/命令 | 从 Makefile/scripts/package.json scripts 反推 |
| `scope` | 文件边界（该模块覆盖哪些文件/目录） | 目录路径 |
| `source_files` | 关键源文件列表 | 枚举结果 |
| `dependencies` | depends_on 边（代码级依赖，事实性） | 从 import/use/requires 反推 |
| `related` | related_to 边（LLM 推断的语义邻居） | 从命名/职责推断 |
| `domain` | **业务领域标签**——该模块属于哪个业务领域 | 从模块职责、命名、所在分层推断（见下） |

提取原则：
- **不臆造**：每个声明须有代码依据。无法确证的标 `(推断)`，高置信但未经注释确证的标 `(高置信推断)`。
- **聚焦业务能力**：剔除审计基类、日志表、纯技术中间表、内部 helper、工具方法等噪音。
- **description 聚焦"功能"而非"位置"**：不要说"这个模块在 src/service/ 下"，应该说"这个模块负责燃气供需匹配的核心算法编排"。
- **architecture_design 是主信号**：这是后续文章正文的主要内容来源，提取时要扎实。

### 3.5 提取业务领域标签（domain）

为每个模块标注**业务领域标签**，供阶段2章节规划使用。标签从以下候选集中选择（可组合，可新增）：

| 领域标签 | 覆盖内容 |
|---|---|
| `概览` | 项目概述、README、快速上手、核心概念 |
| `架构` | 整体设计、分层策略、核心抽象、模块间协作 |
| `核心业务` | 主要业务功能、领域逻辑、业务规则 |
| `数据层` | 数据访问、存储、缓存、ORM、数据库 |
| `API层` | HTTP/RPC 接口、路由、控制器、网关 |
| `前端` | UI 组件、页面、路由、状态管理（纯后端仓跳过） |
| `基础设施` | 构建、部署、CI/CD、容器化、监控 |
| `集成` | 外部系统集成、消息队列、第三方服务 |
| `工具` | 通用工具、辅助函数、内部 helper |
| `测试` | 测试框架、测试用例、质量保障 |

标注方法：
1. 从模块的 `description` 和所在源码目录推断
2. 一个模块可标注多个领域（如 `核心业务` + `数据层`），但须选一个**主领域**
3. 标注结果记录在 `.module-tree.md` 中

> 领域标签是章节规划的输入，不是最终章节名。阶段2会将领域相近的模块聚合为章节。

### 4. 大项目只读并行子代理

单代理无法在上下文内装下大库，不分区并行就必然漏模块。判定项目规模：

| 规模 | 源码文件数 | 处理 |
|---|---|---|
| 小 | <50 | 单 agent 直接枚举 |
| 中 | 50-200 | 单 agent，按需分区 |
| 大 | >200 | **必须**分区并行 `Explore` 子代理 |

大项目分区并行（核心纪律：子代理只 inspect + summarize，主 agent 负责所有写入）：

1. 按顶层模块/目录分区，每区派发一个 `Explore` 子代理（subagent_type: Explore，只读）。
2. 子代理任务：枚举该区模块 + 提取逐模块知识，产出一个分片清单（markdown）。
3. 子代理**只 inspect + summarize，不写文件**——所有写入由主 agent 完成。
4. 主 agent 合并各分片、去重、统一模块树。
5. 子代理数量：大仓 1-4 个（按分区数定，每区一个）。

子代理 prompt 模板（派发时填充）：

```text
只读探查任务：枚举并提取 <分区路径> 下所有模块的知识。

1. 全量枚举该分区源码树（排除默认 glob）。
2. 对每个模块提取：path / description（业务概述，聚焦能力而非路径）/ architecture_design /
   tech_stack / coding_conventions / unique_setup / scope / source_files /
   dependencies / related / domain（业务领域标签：概览/架构/核心业务/数据层/API层/前端/基础设施/集成/工具/测试）。
3. 描述要说明"这个模块做什么"，不要说"这个模块在哪个目录"。
4. 输出 markdown 分片清单，不要写任何文件、不要修改代码。
5. 不臆造，无法确证标 (推断)。
```

### 5. 内存中保留

模块树在内存中保留，作为：
- 阶段2 章节规划的输入（模块路径 + 业务描述 + 业务领域标签 + 规模提示）。
- 阶段3 覆盖率核对的基线（每个模块须被某篇文章覆盖）。

模块路径须与后续中文文件名映射关系记录在内存中。

每个模块节点格式：

```
<tree-prefix>`<path>` — _<业务描述>_[ [N 子模块]] domain=<主领域标签>
```

示例：

```
/ — _燃气智能体平台_[ [4 子模块]] domain=概览
├── skills/ — _可插拔 AI 技能集合_[ [6 子模块]] domain=核心业务
│   ├── ontology-modeling/ — _燃气业务本体建模，管理实体、关系与术语库定义_ domain=核心业务
│   ├── code-generation/ — _根据需求自动生成业务代码_ domain=核心业务
│   └── code-verification/ — _生成代码的自动化验证与质量检查_ domain=测试
├── docs/ — _项目文档与规范_ domain=概览
└── manifest.json — _平台入口：技能清单、路由、依赖声明_ domain=架构
```

## 准出（阶段1）

- 模块树覆盖整棵源码树（默认 glob 之外无遗漏）。
- 每个模块有 description（业务功能描述）+ domain（业务领域标签）；重要模块有 architecture_design。
- 依赖与相关边已提取（可为空，但不可臆造）。
- 模块树在内存中保留，供阶段2使用。
