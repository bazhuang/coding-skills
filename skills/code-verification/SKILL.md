# 代码验证

对已生成的代码进行交付前的质量验证。code-generation 只负责生成代码文件，不执行任何验证；本 skill 是对最终产出的全面质量把关。

## 输入

| 输入文件 | 作用 |
|---------|------|
| `docs/app-design.md` | 技术规范合规检查的依据 |
| `docs/db-schema.md` | 数据库设计合规检查的依据 |
| `docs/brd.md` | 功能完整性对照的验收清单 |

## 验证流程

### 步骤 1：技术规范合规检查

对照 `../app-design/references/backend-tech-guidelines.md` 逐条检查生成的代码。

**检查项**（包括但不限于）：

| 检查维度 | 具体项 |
|---------|--------|
| Controller 层 | 方法是否有 `@Authorize` 注解、返回类型是否为 `ServiceResult<VO>` |
| 命名空间 | 是否使用 `jakarta` 而非 `javax` |
| 注解 | PO/DTO/VO 是否使用 `@Data`、Mapper 是否使用 `@Mapper` |
| 分层规范 | Biz/Service 是否直接用实现类（无 interface）、数据转换方向是否为 PO→DTO→VO |
| 审计字段 | 每张表对应的 PO 是否包含 create_by/gmt_create/update_by/gmt_modified |
| 时间类型 | 时间字段是否使用 `java.util.Date` |
| 数据库规范 | 是否存在外键约束、是否使用了 float/double、字段命名是否规范 |

**问题分级**：

| 级别 | 定义 | 处理方式 |
|------|------|---------|
| **Critical** | 技术规范违规（确定性规则，如缺 @Authorize、用了 javax） | **自动修复**，修复后重新检查 |
| **Important** | 编译错误、逻辑缺陷（可能涉及设计决策） | **报告给用户**，由用户决定如何处理 |
| **Minor** | 代码风格、优化建议 | **记录备查**，不阻断流程 |

### 步骤 2：代码质量审查（子代理执行）

派遣独立子代理审查代码质量，提供没有上下文包袱的"新鲜视角"。

**与步骤 1 的区别**：步骤 1 检查"有没有"（规范有没有遵守），步骤 2 检查"好不好"（代码质量、设计合理性、安全风险）。

**子代理输入**：
- 生成代码的 diff 文件（通过 `git diff` 生成）
- `../app-design/references/backend-tech-guidelines.md` 技术规范

**审查关注点**：

| 维度 | 典型问题 |
|------|---------|
| 代码重复 | 多个 Service 中重复相同的逻辑块 |
| 职责边界 | Biz 层是否做了 Service 层该做的事，Service 层是否越权 |
| 异常处理 | 是否吞掉异常、是否有空 catch、业务异常是否明确 |
| 安全风险 | SQL 拼接（MyBatis 中使用 `${}` 而非 `{}`）、未校验的入参 |
| 数据一致性 | 跨对象操作是否有事务保障 |
| 代码可维护性 | 文件是否过大、方法是否过长、命名是否清晰 |

**子代理输出**：审查报告，按 Critical / Important / Minor 分级。

**问题分级与处理**（与步骤 1 相同）：

| 级别 | 处理方式 |
|------|---------|
| Critical | 自动修复 |
| Important | 报告给用户 |
| Minor | 记录备查 |

### 步骤 3：功能完整性对照

将 `docs/brd.md` 中的功能需求与生成的代码进行对照，**自动扫描生成对照清单，用户聚焦未匹配项确认**。

**对照方式**：

1. 从 `docs/brd.md` 的 §4 功能需求章节提取功能点列表
2. 扫描生成的 Controller/BizService 代码，按方法名和注释匹配功能点
3. 生成对照清单：

```
| BRD 功能需求 | 对应代码位置 | 状态 |
|-------------|------------|------|
| 创建合同 | GasContractController.createContract() | ✅ 已匹配 |
| 合同审批 | GasContractBizService.approveContract() | ✅ 已匹配 |
| 利润计算 | ??? | ❌ 未找到对应实现 |
```

4. 将清单呈现给用户，用户重点确认 ❌ 的项目：
   - 如果是命名差异导致未匹配，用户确认后标记为 ✅
   - 如果确实缺失，纳入 Important 问题清单

### 步骤 4：运行验证（条件执行）

逐步引导用户提供运行环境，如果环境不可用则跳过，不强求。

**环境检查顺序**：

1. **JDK + Maven**：是否已安装？能否执行 `mvn compile`？
   - 如果不能 → 跳过运行验证，提示用户安装后重新执行
2. **数据库**：是否有可连接的 MySQL 实例？
   - 引导方式："运行验证需要连接 MySQL 数据库。请提供连接信息（host/port/database/username），或输入 skip 跳过数据库验证。"
   - 如果不能 → 跳过数据库相关验证
3. **应用启动**：能否启动 Spring Boot 应用？
   - 如果不能 → 跳过接口冒烟测试

**运行验证内容**（按环境可用性逐步执行）：

| 环境就绪 | 验证内容 |
|---------|---------|
| Maven 可用 | `mvn compile` 编译通过 |
| 数据库可用 | DDL 建表语句执行成功 |
| 应用可启动 | 接口冒烟测试（POST /api/xxx/create 等端点可达） |

每个环境步骤如果不可用，明确告知用户跳过了什么、后续如何补验。

### 步骤 5：输出验证报告

汇总所有检查结果，生成验证报告：

```markdown
# 代码验证报告

## 技术规范合规
- ✅ 通过：12 项
- 🔧 已自动修复：3 项（列出修复内容）
- ⚠️ 待用户确认：1 项（列出 Important 问题）
- 💡 建议：2 项（列出 Minor 问题）

## 代码质量审查
- ✅ 通过：6 项
- ⚠️ 待用户确认：2 项（如：Biz 层包含计算逻辑应下沉到 Service 层）
- 💡 建议：1 项（如：GasPlanService 方法超过 50 行，建议拆分）

## 功能完整性
- ✅ 已匹配：8 / 10 项
- ❌ 未匹配：2 项（列出，待用户确认）

## 运行验证
- 编译：✅ 通过 / ❌ 失败 / ⏭️ 跳过（原因）
- 数据库：✅ 建表成功 / ⏭️ 跳过（无可用数据库）
- 应用启动：⏭️ 跳过（无法连接数据库）

## 待处理事项
1. [Important] xxx
2. [Important] xxx
```

## 技术规范参照

验证时必须对照 `../app-design/references/backend-tech-guidelines.md` 中的全部技术规范，不可妥协。

## 关键原则

- **验证是交付前的终检**：code-generation 不做任何验证，所有质量检查在本 skill 中完成
- **规范合规 + 代码质量双维度**：步骤 1 检查"有没有"（规范有没有遵守），步骤 2 检查"好不好"（代码质量、设计合理性、安全风险）
- **代码质量审查由子代理执行**：提供没有上下文包袱的"新鲜视角"，避免自己看不到自己的问题
- **分级处理**：Critical 自动修复、Important 报告用户、Minor 记录备查——不过度打断，也不放任问题
- **环境不强求**：逐步引导，有环境就验，没有就跳过，明确告知跳过了什么
- **功能对照半自动**：自动扫描减轻人工负担，人工确认保证准确性
