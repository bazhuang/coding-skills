# 对象-行为-规则建模方法论

本文件提供 ontology-modeling 的详细建模方法、提问方式、规则过滤标准和常见误区。需要细化模型时读取；主流程只保留导航。

## 本体三要素

| 要素 | 定义 | 问题 |
|------|------|------|
| **对象(Object)** | 系统中真实存在的业务实体 | What exists? |
| **行为(Behavior)** | 对象能够执行或承受的动作 | What can be done? |
| **规则(Rules)** | 约束对象状态转换和行为执行的不变式 | What must hold? |

## 双产出映射

| 本体要素 | 本体 Schema 映射 | BRD 文档映射 |
|----------|-----------------|-------------|
| **对象** | `objects[]` + `edges[]` | §3 利益相关方 + §6 数据需求 |
| **行为** | `biz_logic` 中记录 + `sop_flows[]` | §5 业务流程 + §4 功能需求 |
| **规则** | `rules[]` | §7 业务规则 + §4.2 非功能需求 |

## 核心原则

1. **对象是第一性的**：先定义存在什么对象，再定义行为。
2. **行为改变对象状态**：每个行为必然导致至少一个对象的状态变化。
3. **规则是不变式**：无论何时何地，规则永远成立。
4. **对象链即流程**：对象之间的引用关系自然形成业务流转路径。

## 步骤1：需求理解与领域分析

询问用户：

- 要建模的业务领域或功能模块是什么？
- 主要解决什么业务问题？
- 涉及哪些主要的业务实体？

同时推理补充：

- 从业务描述中提取初步的业务实体（对象）。
- 识别可能涉及的业务流程（行为）。
- 发现隐含的业务约束（规则）。

产出：

- 本体 Schema：初始 schema（`domain`、`biz_logic`）
- BRD：§1 项目概述 + §2 业务范围

## 步骤2：对象层(Object Layer)建模

按照优先级识别 4 类对象。

### 核心对象(Core Object)

- **定义**：业务领域的中心实体，具有独立生命周期。
- **特征**：可被创建、查询、更新、删除（CRUD）。
- **表现**：实心圆角矩形，主题色。
- **示例**：合同、订单、用户。

提问：

- 这个业务领域中有哪些具有独立生命周期的中心实体？
- 它们有哪些关键属性？
- 它们有哪些状态？

### 实体对象(Entity Object)

- **定义**：有唯一标识但依赖于核心对象的实体。
- **特征**：有 ID，有生命周期，但必须属于某个核心对象。
- **表现**：细边框圆角矩形。
- **示例**：订单明细（属于订单）、合同条款（属于合同）。

提问：

- 哪些实体有唯一标识但必须依附于核心对象？

### 引用对象(Reference Object)

- **定义**：被多个对象引用的主数据/基础数据。
- **特征**：生命周期独立，变更频率低，多处引用。
- **表现**：椭圆形。
- **示例**：产品目录、客户档案、部门信息。

提问：

- 哪些是被多个对象引用的主数据/基础数据？

### 对象关系(Edge/Relation)

- **定义**：表达对象之间的依赖、归属、引用或流转关系。
- **特征**：有来源对象和目标对象，有方向和约束。
- **表现**：有向连线，约束表达一对一、一对多、多对多或领域约束。
- **示例**：订单包含多个商品；合同生成多张开票。

提问：

- 这些对象之间有哪些方向明确的关系？
- 哪些关系允许一对多或多对多？
- 关系是否有业务约束，如状态、时间、数量、链路一致性？

产出：

- 本体 Schema：`objects[]` + `edges[]`
- BRD：§3 利益相关方 + §6 数据需求

## 步骤3：行为层(Behavior Layer)建模

为每个核心对象识别 5 类行为。

| 行为 | 语义 | 前置条件 | 后置条件 | 提问 |
|---|---|---|---|---|
| Create [C] | 使对象从无到有 | 无对象实例存在 | 对象实例被创建，状态为初始态 | 如何使这个对象从无到有？ |
| Update [U] | 改变对象属性值或状态 | 对象必须存在 | 对象属性或状态已变更 | 如何改变对象的属性值或状态？ |
| Query [Q] | 读取对象但不改变状态 | 对象可能存在或不存在 | 返回对象数据，状态不变 | 需要查询这个对象的哪些信息？ |
| Delete [D] | 使对象失效 | 对象必须存在 | 对象不可再访问或状态为已删除 | 如何使这个对象失效？ |
| Derive [->] | 基于一个对象创建另一个关联对象 | 来源对象存在 | 目标对象被创建并关联来源对象 | 基于这个对象可以创建哪些关联对象？ |

### SOP 执行流程

识别完核心对象行为后，将行为按业务执行顺序组织为 SOP 流程：

- 每条 SOP 流程（SopFlow）代表一个完整的业务执行路径，包含 `code` 和 `title`。
- 流程步骤（SopStep）按实际执行顺序排列，每个步骤包含 `code` 和 `title`。
- 一个 SOP 流程可能跨越多个对象的行为。
- 根据业务复杂度，可以定义多条 SOP 流程，如正常流程、异常流程、审批流程。

产出：

- 本体 Schema：在 `biz_logic` 中记录行为信息，在 `sop_flows[]` 中记录执行流程。
- BRD：§5 业务流程 + §4.1 功能需求。

## 步骤4：规则层(Rules Layer)建模

### 规则提取过滤原则

**只提取对后续应用代码逻辑有直接影响的规则**。

| 需要提取 | 不需要提取 |
|---------|-----------|
| 涉及多对象、多属性的交叉校验逻辑 | 单属性基本校验（如：金额 > 0、名称非空） |
| 开发者无法从 schema 推断的领域知识 | 从对象定义显而易见的约束（如：状态属于枚举值） |
| 直接驱动算法或计算逻辑的核心公式 | 标准 CRUD 前后置条件（如：创建后状态=草稿） |
| 影响业务决策的非显而易见约束 | 简单外键存在性校验（如：合同 ID 必须存在） |
| 跨实体链路一致性校验 | 单表字段类型/范围校验（如：系数在 (0,1]） |

不需要提取的反例：

- ~~plan_quantity > 0~~ -> 基本数据校验
- ~~plan_month 非空~~ -> 字段必填校验
- ~~status 属于 {草稿, 审批中, 已审批}~~ -> 枚举范围定义
- ~~resource_price > 0~~ -> 正数校验
- ~~创建后 status = 草稿~~ -> 显而易见的初始状态
- ~~开票.合同ID 必须存在于合同表~~ -> 标准外键约束

需要提取的正例：

- **利润 = 交付量 * (销售单价 - 资源采购价 - 运力采购价)** -> 业务计算公式
- **is_must_supply=true 的需求不可被忽略** -> 领域约束，驱动算法优先级
- **匹配链路：资源的下载站 = 管输的起始站** -> 跨实体一致性
- **非草稿状态锁定所有池数据** -> 状态驱动的数据隔离逻辑

### 规则类型

#### 业务计算规则(Calculation Rule)

- **定义**：涉及多属性或多对象的计算公式或推导逻辑。
- **特征**：直接驱动应用代码中的计算模块，公式不显而易见。
- **示例**：利润 = 交付量 * (销售单价 - 资源采购价 - 运力采购价)。

提问：

- 这个业务场景中有哪些核心计算公式或推导逻辑？
- 哪些数值需要从其他属性或对象推导出来？

#### 业务约束规则(Business Constraint Rule)

- **定义**：涉及多对象交互、跨实体一致性或领域特定决策的约束逻辑。
- **特征**：约束逻辑跨对象、非显而易见、直接影响算法或流程分支。
- **示例**：保供优先、链路一致性。

提问：

- 有哪些跨对象约束是开发者无法从 schema 直接推断的？
- 有哪些业务决策规则会直接影响算法优先级或分支逻辑？
- 对象之间的关联关系中有哪些非显而易见的一致性要求？

产出：

- 本体 Schema：`rules[]`（仅包含高价值规则）
- BRD：§7 业务规则 + §4.2 非功能需求

## 步骤5：验证与优化

### 核心原则验证

- 对象是第一性的：先定义存在什么对象，再定义行为。
- 行为改变对象状态：每个行为必然导致至少一个对象状态变化。
- 规则是不变式：无论何时何地，规则永远成立。
- 对象链即流程：对象之间的引用关系自然形成业务流转路径。

### 完整性检查

- 所有核心对象是否都有必要行为？
- 所有高价值规则是否符合过滤原则？
- 对象关系是否清晰明确？

### 一致性检查

- 对象命名是否统一规范？
- 行为命名是否清晰表达意图？
- 规则定义是否无歧义？

### BRD 自检

- 项目目标是否明确、可衡量？
- 业务范围是否清晰界定？
- 功能需求是否覆盖所有业务场景？
- 术语是否统一、无歧义？

## 交互指导

### 持续更新 Schema + BRD

- 建模开始时，先读取 `docs/ontology_schema.json` 和 `docs/brd.md`（如果存在），在已有内容基础上继续建模。
- 从识别出第一个对象开始，每次回复都必须更新本地 `docs/ontology_schema.json` 和 `docs/brd.md`。
- 不要等到所有信息收集完毕才生成 schema 和 BRD，而是边建模边输出。
- 每次用户补充信息后，基于最新信息更新完整的双产出文件。
- schema 的 `biz_logic` 字段应持续记录用户的对话输入。
- 对于尚未确定的字段或章节，可以使用合理的初始值或标注“待确认”，后续交互中再更新。
- 回复中只展示摘要和文件路径；用户要求查看全文时，再读取文件并展示相关片段。

### 提问技巧

- 使用开放式问题：“这个业务领域涉及哪些核心实体？”
- 提供示例帮助理解：“比如订单管理系统中的订单、商品等。”
- 追问细节：“这个对象有哪些关键属性？”
- 复述用户的回答确认理解。
- 指出潜在的问题或遗漏。
- 建议更优的建模方案，并解释原因。

### 推理补充策略

当用户提供的信息不够完整时：

1. **基于已有信息推理**：利用上下文和行业常识推断可能的需求。
2. **标注推理来源**：明确说明哪些是用户说的，哪些是推理的。
3. **以建议形式呈现**：使用“建议补充”“可能需要考虑”等措辞。
4. **请用户决策**：所有推理结论都由用户确认或调整。

## 常见问题

### 对象与属性混淆

- **错误**：把“地址”作为核心对象。
- **正确**：地址通常作为属性或值信息，依附于用户/企业等核心对象。

### 行为粒度过大

- **错误**：一个“处理订单”行为包含创建、支付、发货等多个步骤。
- **正确**：拆分为“创建订单”“支付订单”“发货”等多个独立行为。

### 规则定义不明确

- **错误**：“金额要合理”。
- **正确**：“金额 > 0 且金额 <= 合同总金额”。

### 忽略状态机

- **错误**：对象没有明确状态定义。
- **正确**：明确定义对象的所有可能状态及状态转换条件。
