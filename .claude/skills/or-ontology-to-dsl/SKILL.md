# OR Ontology To or_dsl

将 `or_ontology` 优先转换为完整的运筹 DSL `or_dsl`；若输入已经是保留 `or_ontology` 结构的标准化优化输入，也可作为兼容输入直接使用。

术语口径：

- 业务本体：`business_ontology`
- `or_ontology`：运筹建模本体
- 运筹 DSL：`or_dsl`

这个 skill 的职责是生成 `or_dsl` 蓝图，不是生成代码，也不是填充实例数据。

## 适用输入

用户输入通常包括：

1. `or_ontology` JSON
2. 与 `or_dsl` 生成有关的补充建模要求

兼容情况：

- 若输入已经是保留 `or_ontology` 结构的标准化优化输入，也可直接使用

内置参考：

1. `or_ontology` 到 `or_dsl` 规则
   - 读取 [references/ontology-to-dsl-rules.md](references/ontology-to-dsl-rules.md)
2. `or_dsl` Schema
   - 读取 [references/dsl.schema.json](references/dsl.schema.json)
3. 数据读取配置
   - 读取 [references/data_read_config.json](references/data_read_config.json)

## 核心边界

- `or_dsl` 是代码生成蓝图，不是数据容器
- `or_dsl` 定义如何读取数据、如何组织集合参数变量、如何定义目标和约束
- `or_dsl` 不包含实例数据，不列出具体路径实例，不执行求解
- 若输入不足以稳定确定 `or_dsl` 结构，显式提出缺口，不要臆造数据来源

## Workflow

按下面顺序工作，不要跳步。

### 1. 读取 or_ontology

先识别：

- 参与优化的业务表
- 可提取的离散集合
- 可定义为参数的数值字段
- 业务目标及其可拆解的目标子项
- 业务约束及其适用范围
- 是否是基于路径的建模场景
- 是否已经是时间离散后的时段级场景
- 核心决策是否应表达为“路径 x 时段”的路径流量

若输入是兼容的标准化优化输入，也先按 `or_ontology` 视角重建对象关系与约束语义，再进入 `or_dsl` 生成。

若输入包含时间维度字段、时段切片表或时间离散化业务对象，默认按时空建模理解：核心决策不是单纯路径流量，而是每个时段上的路径流量。

### 2. 对照 or_dsl Schema 搭建顶层结构

读取 [references/dsl.schema.json](references/dsl.schema.json)。

输出必须完整包含：

- `meta_info`
- `data_def`
- `decision_vars`
- `objective`
- `constraints`
- `solve_config`
- `output_config`

字段名、层级和类型必须遵循 schema。

### 3. 构建 data_def

读取 [references/ontology-to-dsl-rules.md](references/ontology-to-dsl-rules.md) 中的数据定义规则，并读取 [references/data_read_config.json](references/data_read_config.json) 确认运行期数据对象来源。

重点完成：

- `tables`：从运行期 `tables` 对象的字典键和 DataFrame 字段定义表结构，只保留参与优化计算的表
- `index_sets`：从业务表字段和运行期 `paths` 对象的路径结构中定义集合
- `parameters`：把数值字段映射为模型参数

若场景具有明确时间离散粒度，`index_sets` 必须显式包含对象-时段组合集合。对每个时段切片业务对象，先用该对象的标识维度与时间维度形成组合索引集合。受时间切片影响的参数必须索引到对应的对象-时段组合集合，不能使用裸字段名或把对象集合与某个单独时间字段临时拼接。

若场景同时是路径型与时间离散型，必须额外定义路径-时间可行域。该集合是派生集合，表示“路径在某个时间点是否具备完整可行的对象-时间组合支撑”。路径-时间可行域应由路径集合、路径上关键对象与各对象-时段组合集合共同约束得出，不能直接复用任何单一对象-时段组合集合。路径流量变量必须索引到路径-时间可行域，而不是索引到某一类对象的对象-时段组合集合。

不要把同一张时段切片表中的所有字段都默认视为时段化字段。默认只有数量类、容量类、上下界类、保底类、计划类、最小满足类、强制满足标记类等会随时段切片发生约束口径变化的度量，才索引到对象-时段组合集合。价格类、名称类、状态类、类型类、组织类、参与方类、路径描述类等属性默认不考虑与时间维度的对应关系；价格类参数应按对象集合索引。只有输入明确声明价格随时段变化，才允许价格参数索引到对象-时段组合集合。

不要因为多个参与优化的时段切片表都含有时间维度字段，就默认它们共享同一个时间集合。统一时间集合只能作为有明确输入依据的辅助集合；即使存在统一时间集合，也不能替代对象-时段组合集合。若缺少跨对象时段对齐依据，应保留对象-时段组合集合，并显式指出跨对象时间对齐缺口，不能臆造统一时间域。

对表和字段的裁剪要保守，不能删掉后续目标或约束会引用的数据来源。

### 4. 构建 decision_vars

- 决策变量必须直接服务于目标和约束
- 若是路径型场景，优先定义路径流量变量
- 若同时存在时间离散且输入明确给出统一时间域，可把核心变量定义为基于路径集合与统一时间集合的时空路径流量变量，但约束和参数必须通过对象-时段组合集合校验对应对象与时间组合是否存在
- 若已定义路径-时间可行域，核心路径流量变量必须直接索引路径-时间可行域
- 若存在多个对象-时段组合集合但没有统一时间域依据，不要直接生成跨对象共享时间变量；应先暴露缺少时段对齐关系，或在输入给出时间映射后再建模
- 不要引入输入中没有依据的额外变量体系

这里“不要引入输入中没有依据的额外变量体系”的含义是：

- 不要在已经可以用 `VAR_PATH_FLOW[p, t]` 表达的场景里，再凭空扩张成边流量、节点流量、弧启停、分段切换等新变量体系
- 只有当输入目标、约束或 schema 绑定明确要求时，才补充辅助变量
- 默认先用一个稳定的时空路径流量主变量承载采购、运输、分配的一体化决策

### 5. 构建 objective 与 constraints

- 目标函数拆成 `obj_terms`
- 每个子项都说明来源和业务含义
- 约束逐条落成 `or_dsl` 约束对象
- 路径型场景下，约束优先用路径流量聚合表达
- 时空路径型场景下，先逐条分析每个约束的时间作用域，再决定 `VAR_PATH_FLOW` 在该约束里的时间聚合维度
- 不要先假定所有约束都按单时段约束处理；应根据右项参数、业务语义和约束口径判断左侧应写成 `VAR_PATH_FLOW[p, t]` 的单时段聚合，还是对 `t` 的跨时段聚合
- 在表达式文本中把时间变量显式写出来；不要只在 `index_sets` 里放入 `TIME_PERIODS`，却让 `left_expression` / `expression` 对 `t` 的绑定保持隐式
- 当约束按对象-时间组合生效时，表达式应直接体现对象与时间绑定，不要只在索引集合中隐式传达
- 约束左右两侧的时间粒度必须一致：若左侧是按 `(对象, t)` 聚合，右侧也必须是同一 `(对象, t)` 口径；不要出现左侧含 `t` 而右侧仍是静态 `(对象)` 参数的写法
- 若输入只提供静态上界/下界参数，而没有时段化口径，则要么把该约束明确建成跨时段总量约束，要么显式说明缺少时段化依据；不要把静态右项直接拿来约束单时段左项
- 不要添加路径流量模型不需要的流量守恒约束

### 6. 构建 solve_config 与 output_config

- 默认按规则使用 `scip`
- 求解参数只填稳定、必要的项
- 输出字段围绕决策变量值、目标值和关键结果摘要
- 对时空路径变量，输出口径必须明确为“路径-时段联合结果”；不要把输出写成会掩盖时间维的裸变量别名

## 路径型建模规则

若场景是基于路径的建模，必须遵循：

- 路径集合名称使用 `FEASIBLE_PATHS`
- 若输入存在时段离散，时间集合名称优先使用 `TIME_PERIODS`
- 路径数据来自运行期 `paths` 对象，`paths` 是路径序列列表
- 单条路径序列应表达为节点标识与连接标识交替出现的有序序列
- 路径本身作为索引键，不在 `or_dsl` 中枚举路径实例
- 路径格式写清楚，但不承载具体路径数据
- 时间离散路径场景下，先定义路径-时间可行域，再让核心路径流量变量索引该可行域
- 不要让核心路径流量变量直接索引任一单一对象-时段组合集合
- 约束通过对路径流量变量的过滤与聚合表达，但时间维是否保留在单时段粒度，必须由该约束本身的时间口径决定
- 对象供给、对象消耗、通道能力、强制满足、最小履约等约束不应机械地都写成“每个时段内”的约束；应先判断其右项和业务语义是时段约束还是跨时段总量约束
- 目标项、约束项、输出项中的表达式都要让 `t` 的作用域显式可见，避免只靠外层说明推断
- 只要约束声明了 `TIME_PERIODS`，就检查左右项是否共享同一个 `t` 作用域
- 不要定义边流量变量替代路径流量变量，除非输入明确要求且 schema/场景允许

典型时空表达优先级：

1. 先定义路径集合
2. 再定义受时间切片影响的对象-时段组合集合
3. 若存在路径和时间离散，定义路径-时间可行域
4. 决策变量优先索引路径-时间可行域
5. 受时间切片影响的参数优先映射到对象-时段组合维度；不受时间切片影响的属性参数保留对象维度
6. 先分析每条约束的时间作用域，再决定左侧是对固定时间下路径流量的聚合，还是对时间维做跨时段聚合
7. 输出字段优先显式表达路径-时间结果，不要退化成不带时间说明的路径流量别名
8. 若某约束左侧使用时间变量，右侧也必须使用同一时间口径，除非该约束被明确建模为跨时段聚合约束

若输入里的关键业务对象本身就是时段切片对象，不要把时间维折叠掉后退化成静态路径模型。

## 输出要求

- 输出完整 `or_dsl` JSON
- 必须满足 schema
- 每个数据来源都清晰可追溯
- 命名遵循 schema 中的命名约束
- 若用户要求按固定格式返回，可在说明后输出最终 JSON

## 禁止事项

- 不要输出实例数据
- 不要把路径实例写进 `or_dsl`
- 不要跳过 schema 校验意识随意增删字段
- 不要把 `or_dsl` 直接写成代码实现
- 不要补充没有输入依据的数据表、字段、参数或变量
