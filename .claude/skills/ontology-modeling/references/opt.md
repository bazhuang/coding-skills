# 需供运筹元模型

当未提供额外元模型输入时，使用本文件作为需供运筹元模型输入。

## 业务对象类型

### Resource（资源）

资源是需供业务的核心载体，是由供给端产生、通过线路传输、被需求端消耗/利用，或经过节点进行存储/转化的各类对象，不限形态、属性及存在方式，其核心特性是在节点与线路构成的需供网络中实现流动，是需供链路的核心流转对象。

核心特性：

- 形态无限制：可分为实体资源（如货物、能源、物料）、虚拟资源（如数据、算力、权限、服务、合同权益）；

- 属性可变化：可具备可分割、可合并、可转化、可存储、可计量等特性，支持业务中各类资源形态/属性的动态变化；

- 流动无限制：可单向流动、双向流动，可连续流动、间断流动，可通过实体运输、虚拟传递等多种方式实现转移；

- 关联唯一性：每一项资源的流动均对应唯一的“供给节点-线路-需求节点”（或多节点、多线路）链路，无脱离节点和线路的孤立资源。

补充说明：可能存在“无实体载体”的需供场景（如虚拟服务供给、权限交付）。

识别原则：

- `resource` 优先表示场景中真正被供给、传输、消耗、存储或转化的对象
- `resource` 不优先表示合同、订单、计划、台账、规则、模型、结果、组织主体、流程步骤等管理或承载性对象
- 当输入同时给出“流动对象”和“承载该对象的业务记录”时，应优先把前者识别为 `resource`
- 若某个对象更像资源供给/需求的记录载体，应继续判断其对应的节点角色，而不是直接归为 `resource`

### Node（节点）

节点是资源的产生、消耗、转运、存储、转化的核心载体，是需供网络的核心节点，所有资源的流动均以节点为起点、终点或中转点，节点的核心功能围绕资源的全生命周期展开，覆盖各类特殊业务中的“功能节点”。


- `supply_node`
  - 含义：仅流出，产生/供应资源

- `demand_node`
  - 含义：仅流入，消耗/需求资源

- `passthrough_node`
  - 含义：流入流出，无存储转化资源功能

- `processor_node`
  - 含义：流入流出，转换/处理资源

- `storage_node`
  - 含义：流入流出，存储资源

识别原则：

- `node` 用于承载 `resource` 的产生、消耗、中转、处理或存储，不与 `resource` 处于同一语义层
- 向网络输出资源的一侧，优先识别为 `supply_node`
- 从网络接收并消耗资源的一侧，优先识别为 `demand_node`
- 只承担流入流出、不承担存储或转化功能的中转位置，优先识别为 `passthrough_node`
- 对资源执行加工、变换、处理等作用的对象，优先识别为 `processor_node`
- 对资源执行库存持有、储存释放、时间平移等作用的对象，优先识别为 `storage_node`

### Edge（线路，节点-节点）

线路是连接两个节点、实现资源流动的通道，是需供网络中的线路对象，核心功能是承载资源从一个节点到另一个节点的转移，不限传输方式、传输介质，覆盖各类实体/虚拟的资源传输场景。


- `transport`
  - 含义：实体运输
  - 特征：存在实体运输

- `link`
  - 含义：映射关系
  - 特征：不存在实体运输，只是映射关系

识别原则：

- 具有实体运输、配送、输送、承运、传递承载语义的边，优先识别为 `transport`
- 仅表达映射、归属、可达、连接、挂接关系而不承载实体运输的边，优先识别为 `link`
- 不要把所有节点关系都默认识别为 `transport`

## 使用约束

使用本元模型时，遵循以下约束：

- 所有业务对象都优先映射到上述类型，不先创造新的顶层对象类型
- 若业务对象无法直接落入某一类型，先在输出中说明映射理由，再决定是否拆分角色
- `node` 与 `line` 是顶层分类，不要混淆
- `transport` 与 `link` 的核心区别是是否存在实体运输
- 标准化时优先按“先识别 `resource`，再识别 `node`，最后识别 `edge`”的顺序工作
- 若输入明确存在供给语义，结果中通常应存在至少一个 `supply_node`
- 若输入明确存在需求语义，结果中通常应存在至少一个 `demand_node`
- 若输入明确存在资源流动、传输、配送、连接或匹配语义，结果中通常应存在至少一个 `edge`
- 在典型需供网络中，`resource`、`supply_node`、`demand_node` 不应互相替代或混写
