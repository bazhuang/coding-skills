# BRD 文档生成

使用**对象(Object)、行为(Behavior)、规则(Rules)**三要素方法论，通过业务访谈直接产出 BRD 文档。

## 数据输出

每次生成的 BRD 文档默认写入本地 `docs/` 目录，后续交互在已有数据基础上进行增量修改。对话输出使用 `<artifact>` 标签区分内容类型（`type="brd"` 用于 BRD 文档）。

### 文件路径约定

| 产出物 | 文件路径 | 格式 |
|--------|---------|------|
| BRD 文档 | `docs/brd.md` | Markdown（符合 BRD 模板结构） |

### 读写规则

1. **建模开始前**：检查 `docs/` 目录下是否已存在 `brd.md`
   - 如果存在：读取现有文件内容，作为当前 BRD 生成的基础，在对话中告知用户"已加载上次的BRD进度"
   - 如果不存在：从零开始生成

2. **每次交互结束时**：将最新的 BRD 默认直接写入本地对应文件
   - 将完整的 BRD Markdown 内容写入 `docs/brd.md`
   - 每次覆盖写入完整内容（非增量），确保文件始终是最新状态

3. **跨会话延续**：不同 Claude Code 会话可以通过读取本地文件恢复 BRD 生成进度
   - 用户可以说"继续上次的BRD生成"，skill 读取文件后从中断处继续
   - 用户也可以提供新的业务材料，skill 读取后补充到现有BRD中

### 与已有业务材料的整合

当用户提供已有的业务材料时：
- 读取材料内容，提取其中的业务需求信息
- 与现有的 `docs/brd.md` 进行合并
- 新发现的需求、流程、规则补充到现有文件中，不覆盖已有内容
- 如果存在冲突，向用户确认后决定保留哪个版本

## 核心方法论

### 本体三要素

| 要素 | 定义 | 问题 |
|------|------|------|
| **对象(Object)** | 系统中真实存在的业务实体 | What exists? |
| **行为(Behavior)** | 对象能够执行或承受的动作 | What can be done? |
| **规则(Rules)** | 约束对象状态转换和行为执行的不变式 | What must hold? |

### 三要素到BRD的映射

| 本体要素 | BRD 文档映射 |
|----------|-------------|
| **对象** | §3 利益相关方 + §6 数据需求 |
| **行为** | §5 业务流程 + §4 功能需求 |
| **规则** | §7 业务规则 + §4.2 非功能需求 |

## BRD 文档结构

BRD 文档包含以下章节：

| BRD 章节 | 内容说明 |
|---------|---------|
| §1 项目概述 | 项目背景、目标、预期收益 |
| §2 业务范围 | 包含/不包含范围、系统边界 |
| §3 利益相关方 | 参与角色、部门、职责 |
| §4 业务需求 | 功能需求（必须有/应该有/可选）+ 非功能需求 |
| §5 业务流程 | 主流程、异常流程、审批流程 |
| §6 数据需求 | 核心实体、属性、关系、数据生命周期 |
| §7 业务规则 | 数据校验、流程流转、权限、计算规则 |
| §8 约束与假设 | 技术约束、业务约束、前置假设 |
| §9 风险分析 | 业务风险、技术风险、应对策略 |
| §10 术语表 | 业务术语定义、缩写对照 |

## BRD 生成流程

### 步骤1：需求理解与领域分析

询问用户：
- 要生成的BRD针对什么业务领域或功能模块？
- 主要解决什么业务问题？
- 涉及哪些主要的业务实体？

**产出**：
- BRD：§1 项目概述 + §2 业务范围

### 步骤2：利益相关方识别

识别业务场景中的关键角色和部门：
- 谁是这个业务场景的主要参与者？
- 有哪些部门或组织涉及其中？
- 每个角色的职责是什么？

**产出**：
- BRD：§3 利益相关方

### 步骤3：业务需求收集

收集功能需求和非功能需求：

#### 功能需求
- 用户必须能够完成哪些核心操作？
- 系统应该提供哪些主要功能？
- 有哪些可选的增强功能？

#### 非功能需求
- 性能要求（响应时间、并发量）
- 安全要求（权限控制、数据加密）
- 可用性要求（系统可用性、容错能力）
- 可扩展性要求

**产出**：
- BRD：§4 业务需求

### 步骤4：业务流程分析

分析业务执行流程：
- 主要的业务执行步骤是什么？
- 涉及哪些业务对象？
- 有哪些异常处理流程？
- 是否需要审批流程？
- 各环节的角色分工是什么？

**产出**：
- BRD：§5 业务流程

### 步骤5：数据需求分析

分析数据层面的需求：
- 涉及哪些核心业务实体？
- 每个实体有哪些关键属性？
- 实体之间的关联关系是什么？
- 数据的生命周期如何管理？

**产出**：
- BRD：§6 数据需求

### 步骤6：业务规则提取

提取关键的业务规则：

#### 业务计算规则
- 有哪些核心的计算公式或推导逻辑？
- 哪些数值是需要从其他属性或对象推导出来的？

#### 业务约束规则
- 有哪些跨对象的约束逻辑是开发者无法从 schema 直接推断的？
- 有哪些决策规则会直接影响系统逻辑？
- 对象之间的关联关系中有什么一致性要求？

**产出**：
- BRD：§7 业务规则

### 步骤7：约束与风险分析

分析技术约束和业务风险：

#### 约束分析
- 技术约束（技术栈、基础设施限制）
- 业务约束（业务规则、法律法规）
- 预置假设（系统假设使用场景）

#### 风险分析
- 有哪些业务风险？
- 有哪些技术风险？
- 可以采取哪些缓解策略？

**产出**：
- BRD：§8 约束与假设 + §9 风险分析

### 步骤8：术语表整理

整理业务术语：
- 有哪些行业术语需要定义？
- 有哪些缩写需要说明？
- 确保全文术语使用统一

**产出**：
- BRD：§10 术语表

## 持续输出BRD（核心要求）

- **BRD生成开始时，先读取 `docs/brd.md`（如果存在），在已有内容基础上继续生成**
- **从识别出第一个需求开始，每次回复都必须使用 `<artifact>` 标签附带完整的当前 BRD**
- 不要等到所有信息收集完毕才生成 BRD，而是边访谈边输出
- 每次用户补充信息后，基于最新信息更新并输出完整的 BRD
- 对于尚未确定的章节，可以使用合理的初始值或标注"待确认"，后续交互中再更新
- **每次回复结束后，默认直接将最新的BRD写入本地文件 `docs/brd.md`**

## 输出格式规范

每次回复由两部分组成：

```
<artifact type="brd">
[BRD 文档的完整 Markdown 内容，不带代码块包裹]
</artifact>

[对话内容：回应用户输入、分析业务、提出下一步问题]
```

## 交互指导

### 循序渐进
- 不要一次性抛出所有问题
- 按照章节逐步引导用户
- 每完成一个章节再进入下一个

### 提问技巧
- 使用开放式问题："这个业务场景的主要目的是什么？"
- 提供示例帮助理解："比如订单管理系统中的订单创建、支付等"
- 追问细节："这个流程有哪些具体的执行步骤？"

### 验证理解
- 复述用户的回答确认理解
- 指出潜在的问题或遗漏
- 建议更优的需求描述

### 推理补充策略
当用户提供的信息不够完整时：
1. **基于已有信息推理**：利用上下文和行业常识推断可能的需求
2. **标注推理来源**：明确说明哪些是用户说的，哪些是推理的
3. **以建议形式呈现**：使用"建议补充"、"可能需要考虑"等措辞
4. **请用户决策**：所有推理结论都由用户确认或调整

## 开始BRD生成

当用户提出BRD生成需求时，首先执行以下步骤：

### 0. 检查本地文件与已有进度

1. 检查 `docs/brd.md` 是否存在
   - 如果存在：读取文件内容，告知用户"已加载上次的BRD生成进度"，并展示当前已完成的章节概要
   - 如果不存在：准备从零开始
2. 检查用户当前目录下是否有业务材料文件
   - 如果存在：主动读取并提取其中的业务需求信息，纳入生成基础

### 1. 需求确认

询问用户：
1. 要生成BRD的业务领域或功能模块是什么？
2. 主要解决什么业务问题？
3. 希望BRD涵盖哪些方面的内容？

然后按照上述工作流程逐步引导用户完成BRD生成。

**关键要求：从识别出第一个需求开始，每次回复都必须在末尾使用 `<artifact>` 标签附带完整的当前 BRD。**
- 即使信息不完整，也要基于已知信息生成初始 BRD
- 用户每次补充信息后，立即更新并输出完整 BRD
- 不要等到最后才一次性生成 BRD
- **每次回复结束后，默认直接将最新的BRD持久化到本地文件 `docs/brd.md`**
- **每次新会话开始时，先读取本地文件，在已有基础上继续生成BRD**
