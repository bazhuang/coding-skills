# BRD 业务需求文档生成

结合**本体方法论(Object-Behavior-Rules)**与大模型推理能力，通过交互式引导，将用户的业务描述转化为结构化的 BRD 文档。

## 核心方法论

### 本体驱动的需求分析

BRD 生成以本体三要素为分析框架，确保业务需求的完整性和一致性：

| 本体要素 | 在 BRD 中的映射 | 分析目标 |
|----------|----------------|---------|
| **对象(Object)** | 业务实体、数据实体、参与角色 | What exists? — 系统中存在什么？ |
| **行为(Behavior)** | 业务流程、功能需求、用户操作 | What can be done? — 能做什么？ |
| **规则(Rules)** | 业务规则、约束条件、验收标准 | What must hold? — 必须满足什么？ |

### 生成原则

1. **以用户输入为主体**：用户描述的业务场景是需求的核心来源，大模型负责结构化梳理而非臆造需求
2. **边分析边输出**：从收集到第一条信息开始，就持续生成和更新 BRD 文档
3. **可确认可调整**：每一步都让用户确认理解是否正确，支持随时调整
4. **推理补充盲区**：基于已有信息推理出可能遗漏的需求点，以建议形式供用户决策

## BRD 文档结构

生成完整的 BRD 文档应包含以下章节：

### 1. 项目概述
- 项目名称与背景
- 项目目标（要解决的业务问题）
- 预期收益与价值

### 2. 业务范围
- 业务范围界定（包含/不包含）
- 涉及的业务领域与部门
- 系统边界与外部依赖

### 3. 利益相关方
- 发起人、决策者
- 业务方代表
- 技术方代表
- 终端用户群体

### 4. 业务需求
#### 4.1 功能需求
- 按业务模块组织的功能点清单
- 每个功能点的详细描述（触发条件、处理逻辑、预期结果）

#### 4.2 非功能需求
- 性能要求
- 安全要求
- 可用性要求
- 兼容性要求

### 5. 业务流程
- 主业务流程（As-Is / To-Be）
- 异常流程
- 审批流程

### 6. 数据需求
- 核心业务实体及其属性
- 实体间关系
- 数据生命周期

### 7. 业务规则
- 数据校验规则
- 流程流转规则
- 权限控制规则
- 计算规则

### 8. 约束与假设
- 技术约束
- 业务约束
- 前置假设

### 9. 风险分析
- 业务风险
- 技术风险
- 应对策略

### 10. 术语表
- 业务术语定义
- 缩写对照

## 生成流程

### 步骤1：业务场景理解

主动询问用户：
- 这个项目/需求的背景是什么？
- 要解决的核心业务问题是什么？
- 涉及哪些业务部门和角色？

**同时**：基于用户已有的描述，主动分析和推理：
- 从业务描述中提取初步的业务实体（对象）
- 识别可能涉及的业务流程（行为）
- 发现隐含的业务约束（规则）

输出：**项目概述**初稿

### 步骤2：对象层分析 — 识别业务实体

基于本体方法论的**对象(Object)**分析，结合用户描述进行推理：

#### 2.1 识别参与角色
- 内部角色：哪些部门/岗位参与？
- 外部角色：客户、供应商、合作伙伴等？
- 系统角色：是否与其他系统交互？

#### 2.2 识别核心业务实体
- 核心实体：业务中最重要的"名词"是什么？
- 辅助实体：支撑核心业务的数据对象有哪些？
- 引用实体：从其他系统引用的数据有哪些？

#### 2.3 识别实体属性与关系
- 每个实体的关键属性
- 实体之间的关联关系（一对多、多对多等）

**提问技巧**：
- "在这个业务中，最重要的'东西'（名词）有哪些？"
- "这些'东西'分别有哪些关键信息需要记录？"
- "它们之间是什么关系？比如一个订单包含多个商品？"

输出：**利益相关方** + **数据需求**初稿

### 步骤3：行为层分析 — 梳理业务流程

基于本体方法论的**行为(Behavior)**分析：

#### 3.1 主流程梳理
- 核心业务流程是什么？（从起点到终点）
- 每个步骤由谁执行？做什么操作？
- 步骤之间的流转条件是什么？

#### 3.2 功能需求推导
- 从流程中提取系统需要支持的功能点
- 每个功能点的输入、处理、输出
- 功能的优先级（必须有 / 应该有 / 可选）

#### 3.3 异常与边界场景
- 正常流程之外的异常情况有哪些？
- 需要支持哪些回退或补偿操作？

**提问技巧**：
- "能否描述一下完整的业务流程，从开始到结束？"
- "每个步骤由谁来完成？需要系统提供什么支持？"
- "如果出了问题，通常怎么处理？"

输出：**业务流程** + **功能需求**初稿

### 步骤4：规则层分析 — 提取业务规则

基于本体方法论的**规则(Rules)**分析：

#### 4.1 数据规则
- 哪些字段有格式要求？
- 哪些字段有范围限制？
- 哪些字段之间有联动关系？

#### 4.2 流程规则
- 什么条件下流程可以推进到下一步？
- 什么条件下需要审批？审批规则是什么？
- 什么条件下需要回退？回退到哪里？

#### 4.3 权限规则
- 不同角色能看到什么数据？
- 不同角色能执行什么操作？
- 是否有数据隔离要求？

#### 4.4 计算规则
- 是否有金额、数量等计算逻辑？
- 计算公式是什么？
- 精度和舍入规则是什么？

**提问技巧**：
- "有哪些'必须满足'的条件或限制？"
- "什么情况下操作会被拒绝？"
- "金额/数量是怎么算的？"

输出：**业务规则** + **非功能需求**初稿

### 步骤5：范围与约束确认

主动梳理并请用户确认：
- 业务范围边界（做什么/不做什么）
- 技术约束（现有系统限制、技术选型等）
- 时间约束（里程碑、交付要求）
- 前置假设（哪些是默认成立的前提条件）

**推理补充**：
- 基于行业经验，提醒可能遗漏的常见需求
- 基于已有信息，推断可能存在的隐性约束

输出：**业务范围** + **约束与假设** + **风险分析**初稿

### 步骤6：整合输出与迭代确认

#### 6.1 生成完整 BRD 文档

将前5步的所有产出整合为一份完整的 BRD 文档，包含：
- 完整的文档结构（上述10个章节）
- 结构化的表格、列表
- 清晰的流程描述

#### 6.2 自检清单

生成后主动检查：
- [ ] 项目目标是否明确、可衡量？
- [ ] 业务范围是否清晰界定？
- [ ] 所有利益相关方是否都已识别？
- [ ] 功能需求是否覆盖所有业务场景？
- [ ] 业务规则是否有遗漏？
- [ ] 是否存在模糊或歧义的描述？
- [ ] 非功能需求是否合理？
- [ ] 术语是否统一、无歧义？

#### 6.3 用户确认

将完整文档提交给用户：
1. 请用户逐章节确认
2. 标记需要调整的部分
3. 迭代修改直到用户满意

## 交互指导

### 持续输出文档（核心要求）

- **从步骤1开始，每次回复都必须附带当前已生成的 BRD 文档内容**
- 不要等到所有信息收集完毕才生成文档
- 用户每次补充信息后，基于最新信息更新并输出对应章节
- 对于尚未确定的章节，标注"待确认"，后续交互中补充

### 循序渐进

- 按照步骤1-6逐步引导用户
- 每个步骤聚焦一个主题
- 完成一个步骤再进入下一个
- 用户可以随时回到之前的步骤补充信息

### 推理补充策略

当用户提供的信息不够完整时：
1. **基于已有信息推理**：利用上下文和行业常识推断可能的需求
2. **标注推理来源**：明确说明哪些是用户说的，哪些是推理的
3. **以建议形式呈现**：使用"建议补充"、"可能需要考虑"等措辞
4. **请用户决策**：所有推理结论都由用户确认或调整

### 提问技巧

- **开放式启动**："请描述一下你的业务场景和需要解决的问题"
- **具体化追问**："能举个例子说明吗？"
- **验证理解**："我的理解是...，对吗？"
- **引导补充**："除了这些，是否还有...的情况？"
- **优先级确认**："这个需求是必须的还是可选的？"

### 应对复杂场景

- **业务范围大**：引导用户先聚焦核心流程，再逐步扩展
- **需求模糊**：提供具体示例帮助用户明确
- **多方参与**：梳理不同角色的不同视角和需求
- **遗留系统对接**：明确接口方式和数据流向

## 开始生成

当用户提出 BRD 需求时，首先：

1. 欢迎用户，简要说明工作方式
2. 询问核心问题：
   - 这个项目的背景和目标是什么？
   - 要解决什么业务问题？
   - 涉及哪些业务领域或部门？
3. 基于用户回答，开始生成**项目概述**章节

**关键要求：从第一次回复开始，每次都必须附带当前已生成的 BRD 文档内容（即使是部分章节）。**
- 即使信息不完整，也要基于已知信息生成初始内容
- 用户每次补充信息后，立即更新并输出最新文档
- 不要等到最后才一次性生成完整文档
