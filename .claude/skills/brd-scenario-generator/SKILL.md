# BRD 业务场景方案生成器

基于通用BRD模板为不同行业生成标准化的业务需求文档（BRD）。纯业务视角，面向业务人员。

## 触发条件

- 用户使用 /brd-scenario-generator 命令

## 核心原则

- **纯业务语言**：不出现字段名、数据类型、编码、算法、求解器等任何技术词汇
- **步骤精简**：业务流程和 SOP 控制在6步以内
- **行为精简**：用业务动词（制定、录入、生成、审核、查询、删除）描述
- **对象精简**：每个对象用一句话描述角色和核心信息
- **BRD标准格式**：包含文档信息、变更记录、编号体系、术语说明

## 工作流程

### Step 1: 接收输入数据

**输入参数**:
```typescript
{
  ontology: {
    biz_logic: string;      // 业务逻辑描述
    objects: OyObject[];    // 对象列表
    edges: OyEdge[];        // 关系列表
    rules: Rule[];          // 业务规则
    behaviors: Behavior[];  // 行为列表
    sop: SOP[];            // 工作流程
  },
  metadata?: {
    scenario_name?: string;  // 场景名称
    industry?: string;       // 行业
    cycle?: string;          // 周期（日度/月度/年度）
    period?: string;         // 时间段（如"2026年3月"）
  }
}
```

**提取关键信息**:
- 从 `ontology.biz_logic` 提取：行业、核心业务活动、时间周期、业务痛点
- 从 `ontology.objects` 提取：业务对象
- 从 `ontology.edges` 提取：对象关系
- 从 `ontology.rules` 提取：业务规则和约束
- 从 `ontology.behaviors` 提取：业务行为
- 从 `ontology.sop` 提取：业务流程
### Step 2: 读取参考文件

1. `references/通用业务场景方案BRD模板.md` — 参考BRD格式的内容结构做自适应模板、用于生成BRD方案。模板示例仅供格式参考，内容必须根据用户实际行业场景生成。

### Step 3: 提取业务结构

基于 ontology 数据提取业务结构：
- 从 `ontology.objects` 提取**业务对象**（谁在参与这个业务、业务围绕什么展开）
- 从 `ontology.edges` 提取**对象关系**（谁影响谁、谁依赖谁）
- 从 `ontology.rules` 提取**业务规则**（业务约束和不变式）
- 从 `ontology.behaviors` 提取**业务行为**（核心操作动作）

### Step 4: 生成BRD方案

> **注意：** 各章节编号数量不是固定的，应根据业务场景的实际复杂度自适应生成。参见下方"编号规则"中的数量范围。

#### 文档信息
包含：文档名称（含时间周期和场景名称）、版本V1.0、编制日期、状态草稿

#### 变更记录
初始版本记录

#### 目录
带锚点链接的章节目录（共10章）：
1. 业务背景
2. 核心目标
3. 业务流程（含 SOP 操作流程）
4. 价值计算公式
5. 关键约束
6. 业务对象
7. 对象关系
8. 业务规则
9. 业务行为
10. 术语说明

#### 1. 业务背景

**输入来源**: `ontology.biz_logic`（业务逻辑描述）

**生成规则**:
从 `ontology.biz_logic` 中提取并组织成1-2段业务背景（50-150字）：
- 第1句：[行业] + [核心业务活动] + 业务定位
- 第2句：在 [时间周期] 内完成 [关键任务]
- 第3句（可选）：当前痛点 + 解决方向

**示例**:
> 天然气供需匹配是能源行业的核心运营场景，需要在月度周期内完成资源调配、运输规划、需求满足的全链条决策。当前人工匹配效率低、约束条件难以全面考虑，需要通过系统化手段实现自动化匹配和优化。

**特殊处理**:
- 若 `biz_logic` 为空或过短（<20字），标注 `{{待补充：业务背景描述}}`
- 禁止出现技术术语，使用纯业务语言

#### 2. 核心目标

**输入来源**: `ontology.biz_logic`、`ontology.rules`

**生成规则**:
- 从 `biz_logic` 中识别目标关键词（提升、降低、优化、确保、实现）
- 从 `rules` 中推断约束目标
- 编号G1起，生成3-5个目标，含说明和优先级（高/中/低）

#### 3. 业务流程（含 SOP 操作流程）

**输入来源**: `ontology.sop`（标准操作流程）、`ontology.behaviors`（行为列表）

**生成规则**:
1. 从 `ontology.sop` 提取流程步骤
   - 若步骤数 ≤ 6：直接使用，丰富描述
   - 若步骤数 > 6：合并相似步骤，精简到6步

2. 丰富每个步骤的描述
   - 使用业务动词：制定、录入、生成、审核、查询、删除
   - 补充业务细节：在括号中说明操作对象或关键信息
   
   **转换示例**:
   > "创建计划" → "制定经营计划（目标、策略、约束条件）"  
   > "录入数据" → "录入供给侧数据（资源容量、成本、合约条款）"  
   > "生成结果" → "系统自动匹配，生成最优分配方案"

3. 为每个步骤标注**操作角色**（业务人员 / 系统），角色判断规则：
   - `ontology.behaviors` 中 type 为 C（创建）、U（更新）、D（删除）的操作 → **业务人员**
   - `ontology.behaviors` 中 type 为 R（查询）的操作 → 视场景而定
   - 含"自动"、"生成"、"计算"、"匹配"等关键词的步骤 → **系统**
   - 含"审核"、"确认"、"制定"、"录入"等关键词的步骤 → **业务人员**

4. 输出格式：表格，3-6步

   | 步骤 | 操作角色 | 操作描述 |
   |:---:|:------:|---------|
   | 1 | 业务人员 | ... |
   | 2 | 系统 | ... |

**特殊处理**:
- 若 `sop` 为空，从 `ontology.behaviors` 推断基本流程（创建→更新→查询→删除），并自动分配角色
- 若步骤过于技术化，转换为业务语言

#### 4. 价值计算公式
核心价值指标 = 正向项 − 各项成本，标注触发条件

#### 5. 关键约束
编号C1起，根据场景实际需要生成（通常3-5个），含维度、约束规则、违反后果

#### 6. 业务对象
编号O1起，根据场景实际需要生成（通常3-7个），每个用一句话描述角色和核心业务信息

#### 7. 对象关系
编号R1起，根据对象数量和实际关系生成（通常4-8个），描述源对象到目标对象的业务关系

#### 8. 业务规则
编号BR1起，根据场景复杂度生成（通常6-15条），按维度分组

#### 9. 业务行为
编号A1起，根据场景实际需要生成（通常4-8个），用业务动词描述核心操作

#### 10. 术语说明
列出本行业的关键业务术语及说明

## 编号规则

| 前缀 | 含义 | 数量范围 |
|:---:|------|------|
| G | 核心目标 | 3-5个 |
| C | 关键约束 | 3-5个 |
| O | 业务对象 | 3-7个 |
| R | 对象关系 | 4-8个 |
| BR | 业务规则 | 6-15条 |
| A | 业务行为 | 4-8个 |

## 质量要求

- 不编造知识库未提及的内容，缺失信息用 `{{待补充：xxx}}` 标注
- 行业术语准确，全文使用行业业务语言
- 时间周期贯穿全文（计划名称、目标描述、SOP步骤中都体现具体时间）
- 排版样式与BRD模板一致（表格对齐、编号统一、章节间用分隔线）
- 不出现任何技术术语（字段名、数据类型、算法、编码等）

### Step 5: 质量自检

BRD 生成完成后，必须逐条核查以下项目，发现问题立即修正后再输出：

1. **技术术语检查**：全文是否出现字段名（如 `cvcu_id`、`create_by`）、数据类型（`String`、`Integer`）、技术类型名（`Resource`、`Node`、`Supply Node`）、实现描述（算法、求解器、优化模型）等技术词汇
2. **时间周期一致性**：时间周期是否贯穿业务背景、核心目标、SOP 步骤等所有章节
3. **编号连续性**：各章节编号（G/C/O/R/BR/A）是否从1开始连续递增，无跳号或重复
4. **对象引用完整性**："对象关系"中的源对象和目标对象是否都在"业务对象"章节中定义过
5. **待补充标注合理性**：`{{待补充：xxx}}` 标注是否仅用于确实缺失的信息，未被滥用

## 保存BRD文档

当用户明确要求保存文案时（如"保存文案"、"保存文档"等），将当前最新的完整 BRD 文案（文档信息、变更记录、目录、全部10个章节）使用 `mcp__graph__data_write` tool 写入到项目根目录下的 `brd-{fingerprint}-{date}.md` 文件中，其中 `{fingerprint}` 的值是根目录下 `.app_config.json` 中 key=fingerprint 的 value 值，`{date}` 为当前日期，格式 `yyyy-MM-dd`。同一 fingerprint 同一日期只维护一份文件，再次保存时覆盖。

**注意：必须使用 `mcp__graph__data_write` tool**
