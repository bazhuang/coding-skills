# 需求分析 Skill

> **阶段定位**：软件开发第一阶段。本阶段完成后，进入 [概要设计阶段](../high-level-design/SKILL.md)。

将业务需求、架构师输入转化为完整的需求规格说明文档。本体图谱是可选输入，有则用，无则基于用户提供的业务输入进行分析。

## 检查清单

按顺序完成：

1. **分析业务输入** — 搜索项目中的本体图谱文件，如果没有则基于用户提供的业务输入
2. **分析本体组件** — 提取 objects、edges、rules、behaviors、sop 的业务含义
3. **推导需求信息** — 从本体图谱推导功能需求、业务流程、约束条件
4. **识别缺失信息** — 确定本体未覆盖的非功能需求和技术约束
5. **针对性提问** — 仅询问本体图谱中缺失或模糊的信息
6. **提出 2-3 种需求方案** — 包含范围权衡和推荐
7. **呈现需求规格** — 按模块分段呈现，每段后获取用户批准
8. **编写需求文档** — 保存到 `docs/requirements/` 并提交
9. **需求自查** — 检查遗漏、矛盾、歧义、可测性
10. **用户审查书面规格** — 要求用户审查规格文件后才能继续

## 流程详解

### 第一步：读取并分析本体图谱

**首先搜索项目中是否有本体图谱文件**：
- 查找 `**/*本体*`、`**/*ontology*`、`**/*模型*` 等模式（不限文件类型）
- 如果找到，读取并分析完整结构

**如果项目没有本体图谱**：
- 基于用户提供的业务输入进行分析
- 通过对话提取业务对象、关系、规则、行为和流程
- 将提取的信息按本体结构组织

**从本体图谱中提取信息（架构师视角）**：

1. **Objects（业务对象）分析**：
   - 识别所有业务实体及其属性
   - 推导功能模块（每个 object 对应 CRUD 操作）
   - 确定实体的业务含义和用途
   - **避免过度设计**：不是所有属性都需要成为需求，关注核心业务属性

2. **Edges（关系）分析**：
   - 识别对象间的关系类型（一对一、一对多、多对多）
   - 推导业务流程和数据关联需求
   - 理解关系的业务语义
   - **避免过度设计**：不是所有关系都需要立即实现，优先核心业务关系

3. **Rules（规则）分析**：
   - 提取业务约束和验证规则
   - 识别数据完整性要求
   - 确定业务不变量
   - **避免过度设计**：区分强制规则和可选规则，优先实现强制规则

4. **Behaviors（行为）分析**：
   - 识别功能需求和业务操作
   - 理解行为的触发条件和执行逻辑
   - 推导用户交互场景
   - **避免过度设计**：关注高频核心行为，低频边缘行为可后续迭代

5. **SOP（标准操作流程）分析**：
   - 理解端到端业务场景
   - 识别流程中的角色和步骤
   - 推导工作流需求
   - **避免过度设计**：识别关键路径和可选路径，优先实现关键路径

**架构师分析原则**：
- **最小可行产品（MVP）思维**：从本体中提取的信息要经过架构师的判断和筛选
- **优先级排序**：不是所有本体元素都同等重要，要区分核心和边缘
- **渐进式设计**：复杂功能可以分阶段实现，不必一次性全部设计
- **业务价值导向**：关注能快速交付业务价值的需求，避免过早优化

**从本体推导的信息**：
- 业务领域和范围（从 objects 类别）
- 关键干系人（从 behaviors 和 sop 的参与者）
- 核心业务流程（从 sop 和 behaviors）
- 业务规则和约束（从 rules）

### 第二步：识别本体图谱未覆盖的信息

**仅针对业务层面的缺失信息提问**（技术问题留到设计阶段）：
- 业务边界和范围（本体未明确的功能边界）
- 业务流程细节（本体 SOP 中缺失的步骤、异常路径、分支条件）
- 业务规则补充（本体 Rules 中未覆盖的业务约束、校验逻辑）
- 业务对象属性补充（本体 Objects 中缺失的属性、枚举值、业务含义）
- 角色和权限（业务参与者及其职责）
- 业务数据要求（数据量级、数据来源、数据归属）
- 业务优先级（哪些是核心功能，哪些是可选功能）

**提问原则**：
- 每次只问一个问题
- 优先使用多选题
- 避免询问本体图谱中已明确的信息
- 技术选型、数据库、性能等非功能需求**不**在此阶段询问

### 第三步：提出需求方案

基于本体图谱分析结果，提出 2-3 种不同范围方案：
- 说明功能模块（基于 objects 和 behaviors）
- 优先级排序（基于 sop 的关键路径）
- 优缺点和成本分析
- 推荐一种方案并解释原因

### 第四步：呈现需求规格

按复杂度分段呈现，每段后等待用户批准：
- 简单项目（1-2 个模块）：一次呈现全部
- 中等项目（3-5 个模块）：按模块分段
- 复杂项目（6+ 个模块）：先核心模块，再扩展模块

### 第五步：编写需求文档

写入单个文件 `docs/requirements/requirements.md`：

**文档重点**：描述**做什么**（What），不涉及技术实现方案

**文档结构**：

1. **项目概述**
   - 项目背景和目标
   - 业务范围和边界
   - 干系人和角色

2. **业务需求**
   - 业务对象及其属性（基于 objects）
   - 业务对象间关系（基于 edges）
   - 业务规则和约束（基于 rules）

3. **功能需求**
   - 功能列表及描述（基于 behaviors）
   - 业务流程和场景（基于 sop）
   - 用户交互要求

4. **业务约束和假设**
   - 业务约束（业务规则、流程限制）
   - 项目约束（时间、资源、范围）
   - 假设条件
   - 验收标准

**注意**：不包含技术选型、架构设计、数据库设计、接口设计等技术实现内容

**写入步骤**：
1. 确保 `docs/requirements/` 目录存在
2. 写入单个 `requirements.md` 文件
3. 提交到 git

### 第六步：需求自查

在要求用户审查之前，快速检查：
- 是否有遗漏的功能模块？
- 是否有矛盾的需求？
- 是否有模糊的描述？
- 需求是否可测试？

### 第七步：用户审查（HARD-GATE）

完成文档后，要求用户审查：

```
需求规格文档已完成，请审查：
- docs/requirements/requirements.md

请确认需求是否完整、清晰、可行。
确认后我们将进入概要设计阶段。
```

**在用户明确确认之前，不得进入下一阶段。**

## 本体图谱映射规则

本体图谱结构：

```javascript
{
  "objects": [...],      // 业务对象定义
  "edges": [...],        // 对象间关系定义
  "rules": [...],        // 业务规则和约束
  "behaviors": [...],    // 业务行为和操作
  "sop": [...]          // 标准操作流程
}
```

**映射到需求文档**：
- **Objects（业务对象）** → 功能模块的 CRUD 需求，数据实体定义
- **Edges（关系）** → 业务流程需求，数据关联需求
- **Rules（业务规则）** → 业务约束，验证需求，数据完整性要求
- **Behaviors（行为）** → 功能需求，业务操作，用户交互场景
- **SOP（标准操作流程）** → 端到端业务场景，工作流需求，角色权限需求
