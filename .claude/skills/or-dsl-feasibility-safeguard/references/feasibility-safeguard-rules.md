# DSL 可行域保障规则

本文件给出对运筹 DSL 进行约束松弛和可行域保障时的规则。

## 1. 任务定位

- 输入是一份完整 OR DSL
- 输出仍然是一份完整 OR DSL
- 目标是在不改变核心业务逻辑的前提下，提升模型可解性
- 只修改 `decision_vars`、`objective`、`constraints`

## 2. 候选约束范围

只考虑边界类约束：

- 上限类：`实际执行量 ≤ 边界值`
- 下限类：`实际执行量 ≥ 边界值`

以下约束不得软化：

- 数学定义类约束
- 变量定义域约束
- 守恒定律类约束
- 决策逻辑定义约束
- 可达性、拓扑、集合映射、索引合法性约束
- 明确标注为安全红线、法规红线、不可突破的核心约束

## 3. 约束分类

在设计松弛前，必须先对每条候选约束做两层分类：

1. 资源型 / 非资源型
2. 上限 / 下限

### 3.1 资源型约束

资源型约束指边界可通过调度、协调、计划重排、合同调整、策略调整等方式改变的约束。这里的“资源型”不是狭义资源对象，而是所有可重新分配、重新承诺、重新协调的业务边界。

典型例子：

- 可分配供给上限
- 客户或区域配额
- 履约目标与保供目标
- 计划最小发运量
- 计划允许使用量

判断要点：

- 能否通过一般业务调度改变
- 约束表达的是承诺、计划、分配、保障还是协调目标

### 3.2 非资源型约束

非资源型约束指由物理结构、设备极限、安全规则、工艺窗口、拓扑连接等决定的刚性边界。

典型例子：

- 设备、线路、仓储、管网容量
- 最小开机量、最低稳定运行量
- 安全上限、安全下限
- 由连接关系决定的结构极限

判断要点：

- 是否不能通过一般调度改变
- 是否需要改造设备、变更工艺或突破安全边界才可能变化

## 4. 松弛优先级

所有可软化约束必须按以下顺序分层放松：

1. 资源型上限
2. 资源型下限
3. 非资源型上限
4. 非资源型下限

这意味着：

- 优先突破资源型上限
- 其次放松资源型下限
- 资源型放开后仍无解，才考虑非资源型上限
- 最后才考虑非资源型下限

## 5. 松弛变量设计

### 5.1 命名规则

变量命名格式：

`VAR_约束对象_约束分类_边界方向_slack`

其中：

- `约束分类` 仅使用 `resource` 或 `nonresource`
- `边界方向` 仅使用 `upper` 或 `lower`

### 5.2 上限约束

- 适用形式：`实际执行量 ≤ 边界值`
- 软化形式：`实际执行量 ≤ 边界值 + VAR_..._upper_slack[索引]`
- 松弛变量非负，表示突破上限的规模

### 5.3 下限约束

- 适用形式：`实际执行量 ≥ 边界值`
- 软化形式：`实际执行量 + VAR_..._lower_slack[索引] ≥ 边界值`
- 松弛变量非负，表示未达下限的缺口

## 6. 惩罚梯度

目标函数中的松弛惩罚必须满足严格顺序：

`资源型上限 < 资源型下限 < 非资源型上限 < 非资源型下限`

默认推荐值：

- 资源型上限：`10`
- 资源型下限：`30`
- 非资源型上限：`100`
- 非资源型下限：`300`

如果模型量纲差异较大，可以等比例放大，但不得改变大小顺序。

计入方式：

- 利润最大化：原利润减去松弛惩罚
- 成本最小化：原成本加上松弛惩罚

## 7. 重构要求

重构后的 DSL 需要完整更新：

- `decision_vars`
- `objective`
- `constraints`

同时保留：

- `meta_info`
- `data_def`
- `solve_config`
- `output_config`

避免无关改动。

## 8. 输出要求

最终输出时先给结构化分析，再给完整 DSL JSON。分析至少包括：

- 约束分类识别
- 可软化约束识别
- 松弛变量设计
- 优先级惩罚设计

最终 JSON 必须满足 DSL schema。
