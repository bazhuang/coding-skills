# 概要设计 Skill

> **阶段定位**：软件开发第二阶段。**前置条件**：需求分析阶段已完成，存在 `docs/requirements/requirements.md`。本阶段完成后，进入 [详细设计阶段](../detailed-design/SKILL.md)。

将需求规格转化为完整的系统架构和概要设计文档。

## 前置条件

**必须先完成需求分析阶段**，并且存在 `docs/requirements/requirements.md` 文件。

如果用户直接要求做概要设计但没有需求文档：
1. 询问是否已有需求文档
2. 如果没有，建议先完成需求分析
3. 如果用户坚持，可以基于用户提供的信息直接进行

## 检查清单

按顺序完成：

1. **读取需求文档** — 从 `docs/requirements/` 读取完整需求规格
2. **读取本体图谱** — 搜索项目中的本体图谱文件，如果没有则基于需求文档分析
3. **分析本体架构** — 从 objects、edges 推导数据架构和模块划分
4. **分析技术约束** — 理解技术栈、架构约束、集成要求
5. **识别缺失信息** — 确定本体和需求未覆盖的架构决策
6. **针对性提问** — 仅询问架构风格、技术选型、部署策略等缺失信息
7. **提出 2-3 种架构方案** — 包含权衡分析和推荐
8. **呈现概要设计** — 按层次分段呈现，每段后获取用户批准
9. **编写设计文档** — 保存到 `docs/design/high-level-design.md` 并提交
10. **设计自查** — 检查一致性、可行性、风险
11. **用户审查书面规格** — 要求用户审查规格文件后才能继续

## 流程详解

### 第一步：读取需求文档

- 检查 `docs/requirements/` 目录下的所有需求文档
- 理解功能需求、非功能需求、约束条件
- 评估系统复杂度

### 第二步：读取并分析本体图谱

**首先搜索项目中是否有本体图谱文件**：
- 查找 `**/*本体*`、`**/*ontology*`、`**/*模型*` 等模式（不限文件类型）
- 如果找到，读取并分析完整结构

**如果项目没有本体图谱**：
- 基于需求文档和用户输入进行分析
- 从需求文档中提取业务对象、关系、规则等信息

**从本体图谱推导架构信息（架构师视角）**：

1. **Objects（业务对象）分析**：
   - 每个 object 对应一个数据库表
   - 每个 object 对应一个服务模块（提供 CRUD 接口）
   - 根据 objects 的分组推导微服务边界
   - **避免过度设计**：不是所有 object 都需要独立服务，相关性强的可以合并

2. **Edges（关系）分析**：
   - **one-to-one 关系** → 在任一表中添加外键字段
   - **one-to-many 关系** → 在"多"的一方添加外键字段
   - **many-to-many 关系** → 创建独立的关联表（表名：`{object1}_{object2}`）
   - 根据关系密度推导模块耦合度
   - **避免过度设计**：不是所有关系都需要立即建立，优先核心业务关系

3. **Rules（规则）分析**：
   - 推导业务逻辑层的验证规则
   - 确定数据完整性约束的实现位置
   - **避免过度设计**：复杂规则可以分阶段实现，先实现强制规则

4. **Behaviors（行为）分析**：
   - 推导服务接口列表
   - 确定业务流程的实现模块
   - **避免过度设计**：关注高频核心接口，低频接口可后续补充

5. **SOP（标准操作流程）分析**：
   - 推导端到端业务流程的服务编排
   - 确定接口调用链路
   - **避免过度设计**：复杂流程可以简化，先实现主流程

**架构师分析原则**：
- **简单优先**：能用简单架构解决的不用复杂架构
- **演进式架构**：从单体开始，必要时再拆分微服务
- **关注点分离**：合理划分模块边界，但避免过度拆分
- **性能与复杂度平衡**：不要为了理论上的性能提升引入过多复杂度

**从本体推导的架构决策**：
- 数据库表结构（从 objects 和 edges）
- 服务模块划分（从 objects 和 behaviors）
- 接口列表（从 behaviors 和 sop）
- 模块依赖关系（从 edges 和 sop）

### 第三步：分析技术约束

从需求文档和项目环境中理解：
- 技术栈约束、架构约束、集成要求、团队能力、现有系统兼容性

### 第四步：推导架构设计

基于需求文档和本体图谱直接推导架构设计：
- 从 objects 推导数据库表和服务模块
- 从 edges 推导模块关系和数据关联
- 从 behaviors 推导接口列表
- 从 sop 推导服务调用链路

**仅在以下情况才提问**：本体图谱或需求文档中有未定义且无法推导的架构决策

### 第五步：提出架构方案

基于本体图谱分析和需求文档，提出 2-3 种不同架构方案：
- 说明架构风格、技术栈
- 模块划分（基于 objects 和 behaviors）
- 数据架构（基于 objects 和 edges）
- 优缺点和性能影响分析
- 推荐一种方案并解释原因

### 第六步：呈现概要设计

按层次分段呈现，每段后等待用户批准：
- 简单项目（单体应用）：一次呈现全部
- 中等项目（3-5 个服务）：先整体架构，再每个服务
- 复杂项目（6+ 个服务）：先整体架构，再核心服务，最后辅助服务

**呈现数据架构时必须包含**：
1. **实体表列表**：列出所有 `objects` 对应的表及其用途
2. **关联表列表**：根据 `edges` 中的 many-to-many 关系，列出所有关联表
3. **表结构设计**：每个表的主要字段（字段名、数据类型、主键、外键）
4. **实体关系图**：展示实体之间的关系（使用 Mermaid ER 图）
5. **表结构设计说明**：说明每个 edge 如何映射到数据库表结构

### 第七步：编写设计文档

将批准的概要设计写入 `docs/design/high-level-design.md`。

**文档重点**：描述**怎么做的整体方案**（How - Architecture），定义系统架构和主要组件

**文档结构**：

**1. 设计概述**
- 系统目标、设计原则、架构风格

**2. 系统架构**
- 整体架构图（使用 Mermaid）
- 架构说明（分层、模块交互）
- 技术栈选择及理由

**3. 模块划分**
- 模块列表及职责（基于 objects 和 behaviors）
- 模块依赖关系（基于 edges 和 sop）

**4. 数据架构**
- 实体关系图（使用 Mermaid ER 图）
- **表结构设计**：每个表的字段定义（字段名、数据类型、主键、外键、审计字段）
- **关联表设计**：many-to-many 关系的关联表结构
- **关系说明**：edge 如何映射到表结构

**5. 接口设计**
- API 列表（路径、方法、功能描述）
- 接口分组（按模块或功能）
- 接口调用链路（基于 sop）

**注意**：不包含具体实现细节（索引设计、字段约束、接口参数格式、类设计、算法实现等）

**写入步骤**：
1. 确保 `docs/design/` 目录存在
2. 分段写入 `high-level-design.md`
3. 提交到 git

### 第八步：设计自查

在要求用户审查之前，快速检查：
- 设计是否与需求一致？
- 架构是否可行？
- 是否有明显的性能瓶颈？
- 是否有单点故障？
- 技术选型是否合理？

### 第九步：用户审查（HARD-GATE）

完成文档后，要求用户审查：

```
概要设计文档已完成，请审查：
- docs/design/high-level-design.md

请确认：
1. 系统架构是否合理？
2. 技术选型是否可行？
3. 模块划分是否清晰？
4. 数据架构是否完整？

确认后我们将进入详细设计阶段。
```

**在用户明确确认之前，不得进入下一阶段。**

## 本体图谱到架构的映射规则

本体图谱结构：

```javascript
{
  "objects": [...],      // 业务对象定义
  "edges": [...],        // 对象间关系定义
  "rules": [...],        // 业务规则和约束
  "behaviors": [...],    // 业务行为和操作
  "sop": [...]          // 标准操作流程
}
```

**映射到系统架构**：

- **Objects（业务对象）** →
  - 数据库表（每个 object 一个表）
  - **表字段定义**：从 object 的属性推导字段名、数据类型、是否主键
  - 服务模块（每个 object 一个 CRUD 服务）
  - 根据 objects 分组推导微服务边界

- **Edges（关系）** → 
  - **one-to-one**：在任一表中添加外键字段
  - **one-to-many**：在"多"的一方添加外键字段
  - **many-to-many**：创建独立的关联表（命名：`{object1}_{object2}`）
  - 根据关系密度推导模块耦合度

- **Rules（业务规则）** → 
  - 业务逻辑层的验证规则
  - 数据完整性约束的实现位置

- **Behaviors（行为）** → 
  - 服务接口定义（API 路径、方法、参数）
  - 业务流程的实现模块

- **SOP（标准操作流程）** → 
  - 端到端业务流程的服务编排
  - 接口调用链路和顺序
