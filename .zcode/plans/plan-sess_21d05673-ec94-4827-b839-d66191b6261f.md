# repo-wiki MVP 升级实施方案（通用化版）

> 目标：在多模块项目上跑出 ≥80 页、目录 3 层、与 Qoder 可对比的产物。skill 内部零技术栈硬编码，任何多模块项目都能用。改动全部落在工作区 `D:\work\external\coding-skills\skills\repo-wiki\`（走 git）。

## 通用性原则（三条，贯穿所有改动）

1. **模块边界以构建系统声明为准**：Maven / Gradle / npm workspaces / Cargo workspace / go work / Nx **平等对待**。模块边界 = 项目作者在构建文件里声明的边界，不靠启发式猜测。
2. **零硬编码**：skill 内不出现任何特定包名、模块名、类名后缀、技术栈假设。需要解析语言特定语法的（如 `depends_on` 的 import 分析）**MVP 留空字段不做**，避免通用化成本拖累 MVP。
3. **章节引导是候选+裁剪，不是强制清单**；门禁阈值相对化（相对 module_count），不用绝对数字。

huitong 在 skill 视角里只是"一个多模块 Maven 项目"的匿名样本，验证时零特殊处理。

## 改动清单（按执行顺序）

### 1. 新增 `scripts/scan_modules.py`（核心）

**作用**：按**构建系统声明**识别多模块项目的模块边界，输出模块树 JSON。

**构建系统检测（平等对待，按命中顺序分派）**：

| 信号文件 | 模块声明位置 | 解析方式 | scope 来源 |
|---|---|---|---|
| `pom.xml`（含 `<modules>`） | `<modules><module>` 子元素 | 标准库 XML 解析 | 各模块目录下源文件 |
| `settings.gradle(.kts)` | `include ':xxx'` | 正则 | 各 include 目录 |
| `package.json`（workspaces）/ `pnpm-workspace.yaml` / `lerna.json` | workspaces 字段 / packages | JSON/简单 YAML 解析 | 各 workspace 目录 |
| `Cargo.toml`（`[workspace]`） | `members` | 手写 TOML 解析（标准库够用） | 各 member 目录 |
| `go.work` | `use` 指令 | 文本解析 | 各 use 目录 |
| `nx.json` + `project.json` | projects | JSON 解析 | 各项目目录 |

每个模块输出（字段全部通用）：
```json
{
  "multi_module": true,
  "module_count": 12,
  "build_system": "maven",        // 检测到的构建系统名，仅描述用
  "leaf_count": 28,
  "modules": [
    {
      "id": "org",                 // 构建系统声明的模块名/artifactId
      "title": "org",
      "type": "aggregate",         // 有 children 为 aggregate，否则 leaf
      "scope": ["org-module/src"],  // 归属目录前缀（正斜杠）
      "children": ["org/distributor"],
      "parent": null
    },
    {
      "id": "org/distributor",
      "title": "distributor",
      "type": "leaf",
      "scope": ["org-module/src/.../distributor"],
      "children": [],
      "parent": "org",
      "depends_on": []            // MVP 始终空，后续阶段补
    }
  ]
}
```

**叶子细化（通用，可选）**：仅当某模块目录文件数 > 阈值（默认 50），按**一级子目录**二次聚类为子模块。纯目录结构驱动，不依赖任何类名后缀/包名。

**降级保证**：单模块项目或无法识别构建系统 → `multi_module: false`，不报错，SKILL.md 据此建议全面模式而非深度模式。

**复用**：输入 `repo_path` 自行遍历（与 scan_repo 同款排除规则）；scope 文件列表用相对路径正斜杠。MVP 不强依赖 scan_api_entries（避免耦合），controllers 可选用于后续校验。

### 2. 修改 `references/structure-prompt.md`

- 第 111 行页面上限按模式分档：精简 4-6 / 全面 15-25 / **深度 80-150**
- 新增 `{MODULES}` 占位符（深度模式专用），注入 scan_modules 的模块树文本（每行：`id | title | type | scope目录 | children`）
- 新增「深度模式」段落，包含：
  - **通用候选章节清单**（不针对特定技术栈，LLM 按项目特征裁剪，不适用的跳过并说明）：
    项目概述 / 架构设计 / 开发指南 / 数据层（若有 schema 或迁移文件）/ 接口层（若有 API 入口）/ 模块详解 / 公共能力（若有 common/util/shared 目录）/ 集成与外部 / 部署运维（若有 Dockerfile/CI）/ 前端（若检测到前端框架）/ 测试（若有显著测试目录）/ 扩展机制
  - **硬约束**：每个识别到的 leaf 模块至少一页（来自模块树）；重要模块可多页。章节组织方式由 LLM 按项目实际决定。
  - 深度模式 XML 写法：复用现有 `section > subsection` 递归表达 3 层，无需新增节点类型。

### 3. 修改 `references/wiki-structure.example.xml`

新增深度模式示例片段（通用，不含特定项目名），展示 `section > subsection（模块组）> subsection（模块）` 三层 page 归属写法。

### 4. 修改 `scripts/parse_structure.py`（轻量，主要验证）

现有 section 解析已递归（扁平 list + `subsections` 引用 + `_find_parent_section` 反推链）。3 层嵌套理论上可工作。主要工作是**实测验证** subsection 嵌套 2 层时 `root_section_ids` 和 `parentSection` 正确；改动量小。

### 5. 修改 `scripts/export_wiki.py`

**5a. 放开目录层级**：`build_page_dir` 第 104-105 行 `chain = chain[:2]` → `chain[:3]`。

**5b. 模块级增量**（通用）：
- `meta.yaml` 新增可选 `modules` 段：`{模块id: 聚合hash}`。模块聚合 hash = 该模块 scope 所有文件 hash 的拼接再 sha256。
- 增量两级判断：先比模块 hash → 未变模块内所有 page 整组跳过（快路径）；模块变了再落到 page 级 hash。
- `generate_meta_yaml` 写 modules 段；`read_meta_yaml` 解析 modules 段；兼容无 modules 段的旧 meta（回退 page 级）。
- 模块 scope 来自 scan_modules 输出（通过 structure.json 的 modules 字段传入，步骤 2.5 注入）。

**5c. scope 记录**：structure.json 带 modules 时，meta.yaml 记录 module→scope→pages 映射（够增量用，MVP 不做完整 _index.yaml 导航树）。

### 6. 修改 `SKILL.md`

- **步骤 3**：模式选择增「深度模式」分支。
- **步骤 4**：深度模式按**模块组**分批派发子 agent（非纯 importance）。
- **模式说明表**（第 253 行）增深度模式行：80-150 页 / 3 层 / 多模块项目。
- 写文件规则补 `docs/tmp/wiki_modules.json`。
- 状态文件补 `scan_modules` 步骤 + `mode=deep`（同步改动 7）。

### 7. 修改 `references/state-ledger.md` + `references/wiki-state.example.yaml`

## 验收标准（通用，可对任何多模块项目验证）

- [ ] 多模块项目生成 ≥80 页、目录 3 层
- [ ] 单模块/无构建系统项目**不触发**深度模式，回退全面模式（不破坏）
- [ ] 深度模式需用户显式确认
- [ ] 模块级增量：第二次生成未变模块整组跳过
- [ ] **skill 内零特定技术栈硬编码**（grep 不出任何特定包名/框架假设）
- [ ] scan_modules 输出可被 LLM 修正
- [ ] 全面/精简模式回归不破坏
- [ ] 所有脚本仅标准库，Windows 路径正斜杠正确
- [ ] 对 huitong 跑通，与 Qoder 产物可对比（huitong 仅作匿名验证样本）

## 实施顺序

1. `scan_modules.py`（新）— 独立可测，先跑通多模块识别（先用任意多模块项目验证，再碰 huitong）
2. `structure-prompt.md` + `wiki-structure.example.xml` — 通用候选清单
3. `parse_structure.py` + `export_wiki.py` — 3 层 + 模块级增量
4. `SKILL.md` + `state-ledger.md` + `wiki-state.example.yaml` — 流程接线
5. `verify_wiki.py` + `verify-checklist.md` — 相对化门禁

## 风险

| 风险 | 缓解 |
|---|---|
| 构建系统解析在某项目格式异常 | 每种构建系统独立 try/except，失败降级为 `multi_module:false`，绝不阻断流程 |
| 3 层目录下 Markdown 链接前缀深度算错 | `build_page_dir` 放开后实测 page-content-prompt 的 `../` 动态前缀逻辑 |
| 80+ 页单次生成慢 | 模块级增量配套 + 按模块组分批 + 用户确认机制 |
| 通用候选清单仍可能不适配某些项目类型 | 候选清单明确"按特征裁剪+扩展"，硬约束仅"每模块至少一页" |

`references/page-content-prompt.md`（单页质量不动）、`scripts/scan_repo.py`、`scripts/scan_api_entries.py`（复用输出不改）、`references/meta-yaml-format.md`（仅 export 写新字段，schema 文档后续补）。
