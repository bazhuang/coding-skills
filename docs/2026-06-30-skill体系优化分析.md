# Skill 体系优化分析

## 背景

当前 gas agents 技能链路为：

`or-workflow-guide -> ontology-modeling -> app-design -> code-generation -> code-verification`

这条链路已经具备端到端能力：从业务描述、本体建模、BRD、应用设计、结构化契约，到代码生成和验证。当前主要优化点不是增加更多 skill，而是控制单个 skill 的上下文体积，并把通用规则沉淀为按需读取的 reference。

## 设计原则

1. **Skill 少而稳**：保留建模、设计、生成、验证四阶段，不继续拆出大量细粒度 skill。
2. **主文件只做流程和路由**：`SKILL.md` 只保留触发条件、执行步骤、门禁和按需读取规则。
3. **细节下沉 references**：数据库规约、技术栈规约、审查清单、契约模板、schema 等放入 `references/`。
4. **可执行规则优先脚本化**：校验、覆盖率、schema 检查等应尽量用脚本或结构化 schema，而不是写成长提示词。
5. **通用检查项不绑定领域**：从天然气案例中抽象出通用设计审查项，如时间区间拆分、主数据编码、单位口径、大字段拆分、异步任务和汇总读模型。

- `SKILL.md` 约 175 行，低于 500 行建议阈值。
- 已经把建模方法、schema 契约、输出契约、需求门禁拆到 references。
- 只需要继续保持，不建议再大幅拆分。

建议后续补充：

- 如果规则过滤示例继续增长，可从 `modeling-methodology.md` 中拆出 `rules-filtering.md`。

- 数据库设计规则具有通用性，应下沉为 `references/db-design-rules.md`。
- 本次天然气方案中暴露的通用设计问题，应沉淀为 `references/design-review-checklist.md`。

已执行的优化方向：

- 主 `SKILL.md` 保留应用设计主流程、硬门禁、产物要求、准出门禁。
- 数据库建模和阿里式 MySQL 规约下沉到 `db-design-rules.md`。
- 通用设计质量审查下沉到 `design-review-checklist.md`。

### or-workflow-guide

当前承担路由、账本、阶段门禁和规格变更处理。短期可保持不动。

未来建议：

- 将账本格式下沉到 `references/progress-ledger.md`。
- 将规格变更传播规则下沉到 `references/spec-change-flow.md`。
- 将阶段门禁摘要下沉到 `references/stage-gates.md`。

### code-generation / code-verification

当前不建议膨胀。

设计原则：

- code-generation 只读取 `app-contract.yaml`、`db-schema.sql`、必要的实现计划。
- code-verification 只读取 `traceability.json`、`acceptance-tests.yaml`、代码和运行结果。
- 不让下游阶段回读 BRD 自由发挥，避免前面结构化契约失效。

## 通用设计审查项沉淀

从本次天然气月度需供匹配案例抽象出的通用检查项：

- 时间范围不得用自由文本字段，拆成 `start_time` / `end_time`。
- 名称类字段如果参与关联、对接或统计，应配稳定 `code` 字段。
- 区域、组织、客户、供应商等主数据应有编码，名称只做展示。
- 气量、价格、金额等口径应有单位和含税/不含税标识。
- 目标函数如果支持综合目标，应有权重字段或策略配置。
- 路径、线路、资源、门站等可复用对象应有稳定编码。
- 大文本快照不放主表，独立拆表。
- 长耗时方案生成采用异步任务，不阻塞同步接口。
- 明细结果之外应考虑汇总读模型，避免每次实时聚合。
- 布尔、状态、枚举字段使用 `tinyint unsigned`。
- 非负数值使用 `decimal unsigned`；可能亏损或差价为负的字段保持有符号 decimal。
- 单表二级索引数量要控制，避免过度索引。

## 建议落地顺序

1. 完成 `app-design` 瘦身和 reference 拆分。
2. 后续再视情况拆 `or-workflow-guide` 的账本和变更传播规则。
3. 暂不新增 skill，避免路由复杂化。
4. 若需要更强确定性，再补轻量校验脚本，而不是继续扩大提示词。

## 本次改动边界说明

本次没有把所有“未来建议”一次性改完，原因是要控制 skill 体系的改动半径。当前优化目标是“降低上下文膨胀，同时保持阶段语义稳定”，不是把所有内容都拆成更细的 skill 或 reference。

本次优先处理 `app-design`，因为它同时满足三个条件：

- **确定收益高**：主 `SKILL.md` 承载了应用设计流程、数据库规约、接口映射、语言选择、可视化伴侣、自审门禁等多类内容，存在继续膨胀风险。
- **风险低**：把数据库规约和设计审查清单下沉到 references，不改变阶段路由，也不改变 code-generation 的输入契约。
- **问题来源明确**：本轮天然气月度需供匹配设计中真实暴露了时间区间、主数据编码、单位口径、大字段拆分、异步任务、汇总读模型、阿里式 DDL 规约等问题，适合沉淀到 `app-design` 的通用 review checklist。

本次实际改动聚焦在三类文件：

- `skills/app-design/SKILL.md`：保留主流程、产物、门禁和按需读取规则，删除大段细则。
- `skills/app-design/references/db-design-rules.md`：承接本体到表结构映射、字段规约、索引规约和 DDL 输出要求。
- `skills/app-design/references/design-review-checklist.md`：承接通用设计审查项，作为 app-design 准出前的质量门禁。

未在本次直接调整的建议及原因如下。

### ontology-modeling 暂不继续拆分

源码版本的 `ontology-modeling/SKILL.md` 已经较健康，约 175 行，并且已经拆出了：

- `modeling-methodology.md`
- `schema-contract.md`
- `output-contract.md`
- `requirements-gate.md`
- `opt.md`

继续拆出 `rules-filtering.md` 或把 `opt.md` 移到 `references/domains/opt.md` 属于进一步精细化治理，不是当前最大瓶颈。若未来规则过滤示例继续增长，再拆会更稳。

### or-workflow-guide 暂不拆分

`or-workflow-guide` 是总 Router，负责阶段路由、进度账本、准出门禁和规格变更传播。它的改动影响范围比 `app-design` 大得多。

如果立即拆出：

- `progress-ledger.md`
- `stage-gates.md`
- `spec-change-flow.md`

需要同步验证会话恢复、阶段跳转、waived 状态、规格指纹、增量重生成等行为。这个改动应单独作为第二批进行，并配回归案例验证。

下一批应优先动 `or-workflow-guide`，不是因为它比其他 skill 更胖，而是因为它已经承担了“系统级控制面”的职责。继续优化它可以降低全链路提示词重复，并让每个阶段只关心自己的准入、准出和权威输入。

### code-generation / code-verification 暂不调整

这两个 skill 当前最重要的设计原则是：依赖结构化契约，而不是回读 BRD 自由发挥。

如果本轮顺手改动，容易扩大范围，影响后续代码生成确定性。更合理的策略是：

- 先稳定上游 `app-contract.yaml` 和 `db-schema.sql`
- 再根据真实生成/验证问题，最小化调整 code-generation 或 code-verification

### 不新增新的 skill

本次没有新增“设计审查 skill”或“数据库规约 skill”。原因是当前阶段划分已经清晰：

`建模 -> 设计 -> 生成 -> 验证`

再新增细粒度 skill 会增加 Router 判断复杂度。设计审查属于 app-design 阶段内部动作，因此更适合做成 `references/design-review-checklist.md`，由 app-design 在准出前按需读取。

## 后续第二批建议

如果继续优化，建议单独开一轮处理 `or-workflow-guide`：

1. 将账本格式拆到 `references/progress-ledger.md`。
2. 将阶段准出门禁拆到 `references/stage-gates.md`。
3. 将规格变更传播和指纹比对拆到 `references/spec-change-flow.md`。
4. 保持 `or-workflow-guide/SKILL.md` 只负责：启动检查、阶段路由、引用相应 reference、更新账本。
5. 准备 3 个回归案例：
   - 从零开始：ontology -> app-design
   - 从已有账本恢复：跳过已完成阶段
   - 上游规格变更：识别受影响下游并更新指纹

第二批完成后，建议用以下标准判断是否达标：

- `or-workflow-guide/SKILL.md` 只保留启动检查、阶段路由、reference 调用说明和账本更新动作。
- 账本格式、阶段门禁、规格变更传播分别有独立 reference，且命名稳定。
- 从零开始、从账本恢复、上游规格变更三类流程都能说明应该读取哪些 reference。
- 下游 `app-design`、`code-generation`、`code-verification` 不需要因此改变输入契约。
- 没有新增额外 skill，Router 判断分支不增加。
