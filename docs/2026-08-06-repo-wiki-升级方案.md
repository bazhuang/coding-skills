## 二、差距根因分析（定位到 skill 实现）

逐条映射到 `repo-wiki` skill 的具体环节，确认改造点。

### 差距 1：页面数量上限被提示词写死（核心瓶颈）

- **现状**：`references/structure-prompt.md:111` 明确要求「8-12 个页面（全面模式）」，`SKILL.md:122` 也固化此范围。
- **后果**：115 vs 11 的 10 倍差距根源在此。LLM 在 8-12 页约束下必然合并多个模块/主题，无法达到 Qoder 的 115 页细粒度。
- **改造点**：`structure-prompt.md`、`SKILL.md` 模式定义。

### 差距 2：缺少「模块/子模块」二维结构生成器

- **现状**：`scan_repo.py` 只产扁平 `file_tree` + `file_hashes`；`scan_api_entries.py` 只扫 API。结构全靠 LLM 从扁平文件树「凭感觉」划分章节。无任何脚本识别**逻辑模块边界**。
- **Qoder 做法**：`_index.yaml` 以 `modules` 字段定义 33 个模块，每个带 `scope`（源文件归属）、`children`（子模块）、`depends_on`/`related_to`（依赖关系）。这是一棵**代码结构驱动的知识树**。
- **改造点**：新增模块识别脚本；结构 XML/JSON 支持「章节 + 子章节 + 模块卡」三级。

### 差距 3：缺少 5 类专属内容类别

repo-wiki 的「全面模式」章节清单（structure-prompt.md:30-39）侧重通用项目（前端/后端/AI 模型/部署），缺失 Java 多模块/企业后端项目的高价值类别：

| 缺失类别 | Qoder 对应目录 | 典型页数 | 缺失原因 |
|---|---|---|---|
| ⚠️ 开发指南 | `开发指南/`（环境搭建/编码规范/测试策略/代码质量/版本管理/扩展开发） | 6 | 提示词未引导 |
| ⚠️ 数据库设计 | `数据库设计/`（架构/规范/索引/迁移/性能/核心模型） | 6+5 | 提示词未引导 |
| ⚠️ API 接口文档 | `API接口文档/`（认证/订单/结算/分销商/平台/接口规范） | 7 | `scan_api_entries` 结果未独立成章 |
| ⚠️ 公共模块 / 门面模块 | `公共模块`、`门面模块`（AOP/工具类/枚举/配置/ERP集成/接口契约） | 5+5 | 无模块卡机制 |
| ⚠️ 横切关注点独立成页 | 异常体系、配置体系、日志体系（Qoder knowledge 卡） | 6 | 提示词无「横切」引导 |

### 差距 4：每模块缺标准化子页面模板

- **现状**：`page-content-prompt.md` 是**单一通用模板**，所有页面同一结构。
- **Qoder 做法**：每个模块卡固定 5 页：`概述 / 技术栈 / 架构设计 / 编码规范 / 特殊配置与命令`（见 `_module.yaml` + 5 个 .md）。叶子模块（如 `huitong_trade/order_management`）也各有这 5 页，保证**全模块同构、可遍历、可检索**。
- **改造点**：`page-content-prompt.md` 拆分为按页面类型的多模板；`agent-contracts.yaml` 新增模块卡生成角色。

### 差距 5：导航/元数据层薄弱

- **现状**：`meta.yaml` 只存页面元数据（id/title/file/source_hash），无层级树、无模块依赖图、无全局导航索引。
- **Qoder 做法**：
  - `_index.yaml`（顶层）：模块树 + scope + depends_on/related_to（可直接画依赖 Mermaid 图）
  - 每模块 `_module.yaml`：模块级导航
  - 每页顶部 `<cite>` 块：统一文件清单
  - `zh/meta/repowiki-metadata.json`：全局统计
- **改造点**：`export_wiki.py` 生成导航产物；`meta-yaml-format.md` 扩展 schema。

### 差距 6：横切知识卡（knowledge）维度缺失

- **现状**：repo-wiki 只产一种文档类型（业务/架构页）。
- **Qoder 做法**：除 `zh/content`（115 页项目文档）外，另有 `knowledge/zh/`（170 个知识卡），覆盖**横切主题**：Maven 依赖管理、Docker 打包、Apollo 配置、SLF4J+Logback 日志、统一异常体系。这些是「跨模块复用、不属于任一业务模块」的底座知识。
- **改造点**：新增 knowledge 生成流程（可选增强，优先级低于前 5 项）。

## 四、升级方案（按优先级排序）

### 🥇 P0 — 提升覆盖广度（直接拉齐 10× 页面差距）

#### 改造 4.1：引入「深度模式」，页面数上限上调

**文件**：`references/structure-prompt.md`、`SKILL.md`（模式说明表）

**改动**：

1. `structure-prompt.md:111` 页面上限从 `8-12` 改为按模式分档：
   - 精简模式：4-6（不变）
   - 全面模式：15-25（上调，适配中小项目）
   - **深度模式（新增）**：80-150，按「章节 → 模块 → 模块卡 5 页」三层结构
2. `structure-prompt.md` 深度模式章节模板新增分类引导（见 4.3）。
3. `SKILL.md:252` 模式说明表新增深度模式行，默认对「检测到 Maven/Gradle 多模块、微服务、monorepo」的项目自动推荐深度模式。

**判定触发**：`scan_repo.py` 检测到多个 `pom.xml`/`build.gradle`/`go.mod` 子模块时，在输出 JSON 加 `multi_module: true` 标志，主 agent 据此建议深度模式。

#### 改造 4.2：新增模块边界识别脚本

**新文件**：`scripts/scan_modules.py`

**作用**：自动识别项目的逻辑模块边界，输出 `_index.yaml` 等价结构，作为深度模式的模块树骨架。

**实现思路**（仅用 Python 标准库，符合 skill 现有约束）：

```
输入：repo_path
输出 JSON：
{
  "modules": [
    {
      "id": "huitong_org/distributor_management",
      "title": "分销商管理",
      "type": "leaf|aggregate",
      "scope": [".../DistributorController.java", ...],   # 归属文件
      "children": ["huitong_org/xxx"],
      "depends_on": [...],        # 由 import 扫描推导
      "parent": "huitong_org"
    }
  ]
}
```

**识别策略**（按框架分派，huitong 走 Maven 分支）：

| 项目类型 | 识别信号 | 模块边界 |
|---|---|---|
| Maven 多模块 | 各 `pom.xml` 的 `<module>` + `<artifactId>` | 每个 artifactId = 一个聚合模块；按包路径再拆叶子 |
| Gradle | `settings.gradle` 的 `include` | 同上 |
| Node monorepo | `package.json` workspaces / pnpm-workspace.yaml | 每个 workspace |
| Python | `setup.cfg`/`pyproject.toml` + 目录 | 每个包 |
| Go | `go.mod` + 多 `main` 包 | 每个 cmd 目录 |

**Maven 叶子模块细化**（对标 Qoder 的 28 叶子）：

- 聚合模块 = 一个 `<module>`
- 叶子模块 = 聚合模块内按「业务子主题」聚合的类组，识别信号：
  - 同名前缀的 Controller/Service/Manager/Domain（如 `Distributor*`）
  - 同一子包路径（如 `com.trinapower.huitong.org.controller` 下按类名聚类）
- 与 `scan_api_entries.py` 的 `controllers` 列表交叉校验，确保叶子模块至少含一个对外入口。

**依赖推导**（`depends_on`/`related_to`）：扫描 `.java` 文件的 `import com.trinapower.*` 语句，统计跨模块引用频次，反向生成模块依赖图。Qoder 的 `_index.yaml` `related_to` 即如此得来。

#### 改造 4.3：扩展深度模式章节分类引导

**文件**：`references/structure-prompt.md`（新增「深度模式」段落）

在深度模式提示词中，强制覆盖以下 12 个顶层章节（对标 Qoder，按项目适用性裁剪）：

```xml
深度模式必须包含以下章节（若项目不适用某章，跳过并说明）：
1. 项目概述      — 背景、目标、核心功能、技术架构概览、快速开始
2. 架构设计      — 整体架构、分布式设计、数据流、技术选型、模块设计详解
3. 开发指南      — 环境搭建、编码规范、测试策略、代码质量、版本管理、扩展开发
4. 数据库设计    — 架构设计、表结构规范、核心数据模型、索引优化、数据迁移、性能调优
5. API 接口文档  — 按业务域拆分（认证/订单/结算/...）+ 接口设计规范
6. 模块详解      — 每个代码模块一张「模块卡」（见 4.4）
7. 公共能力      — AOP 切面、工具类、枚举常量、异常处理、配置管理（横切关注点）
8. 集成与门面    — 外部系统集成（ERP/风控/...）、跨模块 API 契约（facade）
9. 部署运维      — 容器化、环境准备、配置管理、监控告警、日志监控、故障排查
10. 核心业务     — 跨模块业务主链路（状态机、生命周期）
11. 平台能力     — 导入导出、定时任务、消息队列、帮助中心等平台级能力
12. 扩展指南     — 模块注册、自定义处理器、消息消费者扩展
```

#### 改造 4.4：模块卡 5 页标准化模板

**文件**：`references/page-content-prompt.md`（拆分为多模板）、`references/agent-contracts.yaml`

**目标**：每个叶子模块生成固定的 5 个标准页（对标 Qoder 的 `_module.yaml` 同构产物）：

| 页面 | 内容来源约束 |
|---|---|
| `概述.md` | 模块的业务定位、核心能力、对外接口清单、与其他模块关系 |
| `技术栈.md` | 该模块用到的框架/库（从该模块的 pom/import 提取） |
| `架构设计.md` | 模块内分层（Controller→Service→Manager→DAO）、类图、时序图 |
| `编码规范.md` | 该模块特有的编码约束、命名约定、事务边界 |
| `特殊配置与命令.md` | 该模块独有的配置项、构建命令、运行参数 |

**实现**：

1. `page-content-prompt.md` 保留为通用模板，新增 `references/page-templates/module-card-*.md` 5 个子模板。
2. `agent-contracts.yaml` 新增 `module_card_generator` 角色，must_read 模块 scope 文件 + 对应子模板。
3. `parse_structure.py` 解析深度模式 XML 时，为每个 leaf module 自动展开 5 个 page 占位。

### 🥈 P1 — 提升结构深度与导航

#### 改造 4.5：结构 XML 支持三级层级

**文件**：`references/wiki-structure.example.xml`、`scripts/parse_structure.py`

**改动**：XML schema 已支持 `section > subsection > page`，但深度模式需支持「section > module_group > module_card > page」四级。需扩展 `section` 增加 `module_groups` 子节点，`parse_structure.py` 输出 `module_groups` 字段。

#### 改造 4.6：生成全局导航索引（对标 `_index.yaml`）

**文件**：`scripts/export_wiki.py`、`references/meta-yaml-format.md`

**改动**：`export_wiki.py` 除生成 `meta.yaml` 外，新增 `docs/wiki/_index.yaml`：

```yaml
# 全局导航索引（对标 Qoder _index.yaml）
schema_version: 2
modules:
  huitong_org:
    title: 组织模块
    scope: ["huitong-org/"]
    children: [huitong_org/distributor_management, ...]
    depends_on: []
    related_to: [huitong_facade]
  huitong_org/distributor_management:
    title: 分销商管理
    scope: [".../DistributorController.java", ...]
    pages: [概述, 技术栈, 架构设计, 编码规范, 特殊配置与命令]
    depends_on: []
    related_to: [huitong_facade, huitong_org/audit_workflow]
```

价值：可直接渲染站点导航树、画模块依赖 Mermaid 图、支撑增量更新精确到模块。

#### 改造 4.7：每页顶部统一文件清单（对标 `<cite>`）

**文件**：`references/page-content-prompt.md`、`references/agent-contracts.yaml`

**改动**：page-content-prompt 增加规则——H1 标题后、目录前，插入 `<cite>` 块列出本页所有 `filePaths` 的可点击链接（Qoder 每页都有，是可检索性的关键）。现有 `<details>` 块保留在页尾作为扩展清单。

### 🥉 P2 — 丰富度增强（横切知识卡）

#### 改造 4.8：新增横切知识卡（knowledge）生成流程

**作用**：对齐 Qoder `knowledge/zh/` 的横切主题文档。这些主题跨模块，不适合放任一模块卡，需独立识别。

#### 改造 4.9：API 文档独立成章

**文件**：`references/structure-prompt.md`（深度模式章节引导）

**改动**：当前 `scan_api_entries.py` 的结果只作为结构生成的输入提示，未保证生成独立的 API 文档页。深度模式下，强制按业务域（从模块树推导）拆分 API 文档，每个对外提供接口的模块至少产出一页 API 参考（请求/响应/错误码/权限码，对标 Qoder `API接口文档/结算管理接口.md` 33KB）。

### 🏅 P3 — 工程化强化

#### 改造 4.10：增量更新精确到模块

**文件**：`scripts/export_wiki.py`、`references/meta-yaml-format.md`

**现状**：增量以 page 的 `source_hash` 为单位。深度模式有 90-130 页后，全量重算成本高。

**改动**：增量模式引入「模块级 hash」——先比对模块 scope 的聚合 hash，未变模块的 5 张卡整组跳过，降低 80% 的重算量。

#### 改造 4.11：验证门禁扩充

**文件**：`scripts/verify_wiki.py`、`references/verify-checklist.md`

**新增软门禁**：
- 模块卡 5 页齐全性（每个 leaf module 是否 5 页都在）
- 每页 `<cite>` 块存在性
- 深度模式：顶层章节数 ≥ 10、模块卡数 ≥ 20（阈值按检测到的模块数动态调整）

## 六、风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 深度模式 90-130 页生成耗时长（子 agent 多） | 单次全量可能 30-60 分钟 | 4.10 模块级增量；并行批次从 importance 改为「按模块组分批」 |
| 模块识别脚本误判边界（如未识别的包结构） | 模块卡 scope 不准 | `scan_modules.py` 输出中间 JSON 供人工/LLM 校验；结构生成步骤允许 LLM 修正模块树 |
| 知识卡（4.8）可能产出空泛内容 | 横切主题若无源码支撑会注水 | 强制横切卡也走「≥5 源文件引用」软门禁；源码不足的主题跳过 |
| 单页质量稀释 | 为凑页数降低深度 | 保留 page-content-prompt 强约束；模块卡 5 页模板各自有独立结构要求 |
