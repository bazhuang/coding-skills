# repo-wiki Skill 优化分析指导

> 基于《从 Vibe Coding 到 Harness——一套大仓 AI 工程化实战》（TAB 实验平台）与《从 AI Coding 到 Harness Engineering 的端到端工程开发实践》（应用宝活动平台）两篇文章的方法论，对照 repo-wiki skill 当前实现，给出优化方向。

---

## 一、两篇文章的核心方法论提炼

两篇文章分别来自腾讯 TAB 实验平台和应用宝活动平台团队，虽然业务场景不同，但提炼出的 Harness Engineering 核心原则高度一致。下表是两篇文章的交叉提炼：

| 核心原则 | TAB 文章的表述 | 应用宝文章的表述 | repo-wiki 当前状态 |
|---|---|---|---|
| **AI 负责认知，脚本负责执行** | "能写成 bash 的就别让 Agent 跑" | "AI 负责认知，脚本负责执行" | ✅ 已践行：文件扫描、XML 解析、导出均为脚本，LLM 只负责生成结构和内容 |
| **长链路必须状态化** | 13 棒接力赛，checkpoint 文件驱动 | e2e-state.json + product-state.json 状态文件驱动 | ❌ 缺失：流程状态全靠对话上下文传递，无状态文件 |
| **知识库必须结构化** | 26KB 仓库代码导航地图 + 任务看板 | 800+ 结构化文档，三层目录（总览→域→服务） | ⚠️ 部分：生成的 wiki 本身是结构化的，但生成过程没有知识库支撑 |
| **Agent 必须职责隔离** | 4 个 Agent（需求/方案/开发/CR），单一职责 | 12 个专家 Agent，上下文隔离+工具最小权限 | ⚠️ 部分：有 high/medium 并行分批，但无角色契约 |
| **执行步骤必须脚本化** | 7 道门禁脚本，软硬门禁分离 | 15 个流程脚本，消除执行不确定性 | ❌ 缺失：无门禁脚本，无产物验证 |
| **Workflow 比 Prompt 更重要** | "流程一旦变成机器能校验的资产，稳定性上一个台阶" | "流程编排的确定性，胜过反复打磨 prompt" | ❌ 缺失：流程是 SKILL.md 里的自然语言描述，不可校验 |
| **下游不可改上游产物** | "Harness 最重的一条纪律" | "确定的输入输出，可被脚本解析、可被断点恢复" | ✅ 已践行：子 agent 只写自己的 page，不改结构 |
| **基线对比剥夺解释权** | 开发前跑基线快照，只看新增失败 | — | ❌ 缺失：无基线机制，LLM 说"已生成"就算完成 |
| **半自动优于全自动** | 5 个人工关卡，"不能让用户每分钟点一次以上" | "人在其中只负责核心关键阶段的决策" | ❌ 缺失：全流程无人工检查点 |
| **增量更新 + 新鲜度检测** | 仓库导航地图"谁动谁更新" | git hash 对比，过期文档自动标记+增量重生成 | ❌ 缺失：每次全量重新生成，无增量更新 |

## 二、repo-wiki skill 当前架构诊断

### 2.1 已经做对的部分

对照两篇文章，repo-wiki 在以下方面已经符合 Harness Engineering 原则：

1. **脚本与认知分离**（文章核心原则第一条）
   - `scan_repo.py`、`scan_api_entries.py`、`parse_structure.py`、`export_wiki.py` 四个脚本处理确定性工作
   - LLM 只做两件认知工作：生成文档结构（XML）、生成页面内容（Markdown）
   - 这是正确的方向，两篇文章都反复强调"确定性的操作交给脚本"

2. **下游不改上游产物**
   - 子 agent 只写自己的 `/tmp/wiki_pages/<page_id>.md`，不修改 structure.json
   - 符合 TAB 文章"下游不可直接修改上游产物"的纪律

3. **按需加载 reference**
   - SKILL.md 明确"只读取当前任务需要的 reference，不要一次性加载所有细节"
   - 符合应用宝文章"渐进式分层加载"的思想

4. **纯标准库，零依赖**
   - 所有脚本仅用 Python 标准库，降低了环境依赖

### 2.2 关键缺口（按优先级排序）

#### 缺口 1：无状态文件——流程状态全靠对话传递（严重）

**文章依据**：
- TAB 文章："每棒都明确写在流程定义文档里：当前阶段是哪一棒、这一棒要交付什么、下一棒接手前必须看到什么"
- 应用宝文章："以状态文件替代容易被压缩的对话历史""状态脱离上下文落盘，才能稳定续传"

**当前问题**：
repo-wiki 的 7 个步骤（清理→扫描→扫描API→生成结构→逐页生成→导出→验证）全靠 SKILL.md 的自然语言描述。如果对话上下文被压缩，LLM 可能：
- 跳过某个步骤
- 重复执行某个步骤
- 忘记当前进行到哪一步
- 中断后无法恢复

**优化方向**：
引入一个 `/tmp/wiki_state.json` 状态文件，记录：

```json
{
  "repo_path": "/path/to/repo",
  "mode": "full",
  "current_step": "page_generation",
  "steps": {
    "0_cleanup": {"status": "done", "timestamp": "..."},
    "1_scan_repo": {"status": "done", "output": "/tmp/wiki_scan.json"},
    "2_scan_api": {"status": "done", "output": "/tmp/wiki_api_entries.json"},
    "3_generate_structure": {"status": "done", "output": "/tmp/wiki_structure.json"},
    "4_generate_pages": {
      "status": "in_progress",
      "total_pages": 10,
      "completed_pages": ["page-1", "page-2"],
      "pending_pages": ["page-3", "page-4"]
    },
    "5_export": {"status": "pending"},
    "6_verify": {"status": "pending"},
    "7_cleanup": {"status": "pending"}
  }
}
```

每个步骤开始时更新状态，完成后标记 done。中断后重新启动时，LLM 先读状态文件，从断点恢复。

#### 缺口 2：无产物验证门禁——"生成完"全靠 LLM 口头汇报（严重）

**文章依据**：
- TAB 文章第六章："Scripts 的价值不是多了一组工具，是把'完成'这个词的定义权从 AI 手里拿了回来"
- TAB 文章："'做完'不再是'AI 觉得做完了'，而是'统一入口的脚本判定通过了'"

**当前问题**：
SKILL.md 步骤 6"验证产物"只是让 LLM "检查 docs/wiki/ 目录"，这是让 AI 自己审自己——正是 TAB 文章反复警告的"AI 对自己生成的东西天然没有否决欲望"。

当前已修复的"缺失页面警告"是一个进步，但仍不够。

**优化方向**：
新增一个 `verify_wiki.py` 脚本，作为硬门禁，检查：

| 检查项 | 类型 | 判定逻辑 |
|---|---|---|
| 概览页面存在 | 硬门禁 | docs/wiki/ 下存在包含"概览/概述/overview"关键词的 .md 文件 |
| 每个页面文件存在 | 硬门禁 | structure.json 中每个 page 都有对应的 .md 文件 |
| 每页含 H1 标题 | 硬门禁 | 每个页面第一行以 `# ` 开头 |
| 每页含至少 1 个 Mermaid 图表 | 软门禁 | 正则匹配 ` ```mermaid ` 代码块 |
| 每页引用至少 5 个源文件 | 软门禁 | 正则匹配 `来源：` 行，统计不同文件引用数 |
| 每页含至少 1 个表格 | 软门禁 | 正则匹配 Markdown 表格语法 |
| 文件名均为中文或安全字符 | 硬门禁 | 检查文件名无 `/\:*?"<>|` 等非法字符 |
| 页面间链接有效 | 软门禁 | 检查 `[xxx](xxx.md)` 链接指向的文件实际存在 |

脚本退出码：硬门禁失败 → exit 1，软门禁失败 → exit 0 + warning。

#### 缺口 3：无增量更新——每次全量重新生成（中等）

**文章依据**：
- 应用宝文章 3.4："文档新鲜度检测：过期知识比没有知识更危险"
- 应用宝文章："增量模式的关键特性是最小改动原则+人工批注保留"
- TAB 文章："谁动谁更新"

**当前问题**：
SKILL.md 步骤 0 执行 `rm -rf docs/wiki`，每次都全量重建。如果用户对生成的 wiki 做了人工编辑（补充业务背景、修正错误描述），这些修改会全部丢失。

**优化方向**：

1. **引入 git hash 对比**：在 `scan_repo.py` 输出中加入当前仓库的 git commit hash。如果 `docs/wiki/` 下已有上次生成的 wiki，且记录了上次的 hash，则可以判断哪些文件发生了变化。

2. **增量生成模式**：
   - 扫描 git diff 获取变更文件列表
   - 只重新生成"相关文件发生变更的页面"（通过 structure.json 中每个 page 的 filePaths 判断）
   - 未变更的页面保留原内容
   - 对于人工编辑过的页面，在页面头部添加 `<!-- 最后自动生成: YYYY-MM-DD -->` 标记，增量更新时保留人工添加的内容（类似应用宝文章的"高价值内容保留"策略）

3. **新鲜度标记**：如果距离上次生成超过一定时间或 commit 数，在页面顶部添加"⚠️ 本页面可能已过期"标记。

#### 缺口 4：无角色契约——子 agent 缺乏明确的职责边界（中等）

**文章依据**：
- TAB 文章 2.3："每个角色只看自己该看的输入、只产自己该产的输出"
- 应用宝文章 4.2："单一职责""上下文隔离""工具最小权限""确定性的输入输出"

**当前问题**：
SKILL.md 步骤 4 说"派发子 agent 并行生成"，但没有定义子 agent 的角色契约——它该读什么、写什么、不许做什么。当前只靠 `page-content-prompt.md` 作为提示词，但提示词是"建议"，不是"约束"。

**优化方向**：
为页面生成子 agent 定义明确的角色契约（类似 TAB 文章的角色契约表）：

```
角色：页面生成 Agent

必读：
  - references/page-content-prompt.md（提示词模板）
  - /tmp/wiki_structure.json 中本页的 page 定义（title, description, filePaths）
  - filePaths 列表中的源文件内容

必写：
  - /tmp/wiki_pages/<page_id>.md（且仅此文件）

不许做：
  - 修改 structure.json
  - 修改其他 page 的 .md 文件
  - 修改仓库源代码
  - 跳过 page-content-prompt.md 中的任何格式要求
```

将此契约写入 SKILL.md 的步骤 4 中，作为子 agent 的调度约束。

#### 缺口 5：无人工检查点——全流程无人工介入（中等）

**文章依据**：
- TAB 文章第五章："关键节点必须有人""模型对自己生成的东西天然没有否决欲望"
- 应用宝文章："人在其中只负责核心关键阶段的决策和信息补全"

**当前问题**：
repo-wiki 从步骤 1 到步骤 7 全自动执行，没有任何人工检查点。LLM 生成的文档结构（步骤 3）直接被解析并用于后续所有页面生成。如果结构本身有问题（章节划分不合理、页面粒度不对、文件关联错误），所有页面都会基于错误的结构生成，浪费大量 token。

**优化方向**：
在步骤 3（生成文档目录结构）之后、步骤 4（逐页生成内容）之前，增加一个人工检查点：

```
### 3.5 人工确认文档结构

向用户展示生成的文档结构概要：
- 项目标题和描述
- 章节列表（全面模式）或页面列表（精简模式）
- 每个页面的标题、importance、关联文件数

请用户确认：
- [确认] 结构合理，开始生成页面内容
- [修改] 我要调整结构（用户提出修改意见后，重新生成结构）
```

这是 TAB 文章"需求确认"关卡的对应物——花 10-30 秒确认，避免后面浪费 10-30 分钟生成错误内容。

#### 缺口 6：无知识库支撑——生成时缺乏项目全局视野（低，受 skill 定位限制）

**文章依据**：
- TAB 文章第八章："AI 缺乏对整个项目的全局视野""同一个工具方法已经有了，又写了一遍"
- 应用宝文章第三章："知识库是整个 Harness 工程体系的基石"

**当前问题**：
repo-wiki 每次生成时，LLM 只看到 file_tree（文件路径列表）和 README，不了解项目的架构背景、已有的设计文档、历史决策。这可能导致生成的 wiki 缺乏深度。

**优化方向**（需权衡 skill 复杂度）：

1. **轻量方案（推荐）**：在 `scan_repo.py` 中增加可选的"已有文档扫描"——如果仓库中已有 `docs/` 目录，读取其中已有的 .md 文件内容，作为结构生成时的参考上下文。这样 LLM 生成结构时能看到"项目已经有了哪些文档"。

2. **中量方案**：支持读取仓库中的 `ARCHITECTURE.md`、`CONTRIBUTING.md`、`CLAUDE.md`、`AGENTS.md` 等约定文件，作为项目背景知识注入结构生成提示词。

3. **重量方案（不推荐）**：建立独立的知识库工程。这超出了 repo-wiki 作为"一次性文档生成 skill"的定位，两篇文章的知识库工程是独立于文档生成的体系。

#### 缺口 7：多行注解正则不完善——影响 API 入口扫描准确性（低）

**文章依据**：
- 应用宝文章 5.1："应对异构服务拓扑，构建目录解析抽象层"
- 两篇文章都强调"脚本化的约束要可判定"

**当前问题**（已知，已在分析报告中指出）：
`scan_api_entries.py` 的正则无法处理多行注解（Spring 的 `@GetMapping` 换行写法等），会漏掉部分 API 端点。

**优化方向**：
将逐行匹配改为"先合并连续注解行再匹配"的策略：

```python
# 伪代码
for i, line in enumerate(lines):
    # 如果当前行匹配注解开头但未闭合括号，向后合并后续行
    if annotation_started and not annotation_closed:
        merged_line += ' ' + stripped
        if ')' in stripped:
            annotation_closed = True
            match_pattern(merged_line, i - offset)
```

## 三、优化优先级与实施路线

按"影响 × 成本"排序：

| 优先级 | 优化项 | 影响 | 成本 | 建议实施 |
|---|---|---|---|---|
| P0 | 增加状态文件 wiki_state.json | 高（流程可靠性） | 中 | ✅ 优先 |
| P0 | 增加 verify_wiki.py 验证脚本 | 高（产物质量） | 中 | ✅ 优先 |
| P1 | 增加人工确认检查点（步骤 3.5） | 高（避免浪费 token） | 低 | ✅ 尽快 |
| P1 | 定义子 agent 角色契约 | 中（并行质量） | 低 | ✅ 尽快 |
| P2 | 增量更新 + git hash 对比 | 中（用户体验） | 高 | ⏳ 二期 |
| P2 | 已有文档扫描（轻量知识库） | 中（内容深度） | 中 | ⏳ 二期 |
| P3 | 多行注解正则修复 | 低（边缘场景） | 中 | ⏳ 按需 |

## 四、两篇文章中不建议照搬的部分

并非两篇文章的所有实践都适用于 repo-wiki，以下是需要注意的差异：

### 4.1 不需要 13 个阶段 / 12 个 Agent

TAB 文章的 13 个阶段和应用宝的 12 个 Agent 是针对"端到端需求开发"设计的——从 PRD 到 MR 提交。repo-wiki 是"文档生成"skill，本质只有"扫描→生成结构→生成内容→导出"四个核心阶段。过度拆分反而增加复杂度。

TAB 文章自己也说了："4 个 Agent 不是设计出来的，是被问题一步步逼出来的"。repo-wiki 当前 1 个主 agent + N 个并行子 agent 的结构已经足够，不需要为了"像 Harness"而拆分。

### 4.2 不需要 MCP 集成

两篇文章都大量使用 MCP 集成外部系统（TAPD、iWiki、工蜂等）。repo-wiki 是纯文档生成 skill，不涉及外部系统交互，不需要 MCP。

### 4.3 不需要 DAG 编排

应用宝文章的 DAG + Fork-Join 适用于"多任务有依赖关系的并行开发"。repo-wiki 的页面生成是无依赖的纯并行（SKILL.md 已明确"页面间无内容依赖，并行安全"），不需要 DAG。

### 4.4 "禁用 Memory" 不完全适用

应用宝文章提到"严格禁用项目级 Memory 以保障状态隔离"。这是针对"自动化流程跑需求"的场景。repo-wiki 是用户主动触发的文档生成，不是无人值守的自动化流程，Memory 的影响有限。但状态文件（缺口 1）确实需要引入。

---

## 五、一句话总结

repo-wiki skill 在"脚本负责执行、AI 负责认知"这一最核心的 Harness 原则上已经做对了，但缺少两篇文章反复强调的三个工程化要素：**状态化（状态文件驱动流程）**、**可验证（门禁脚本验证产物）**、**可恢复（增量更新而非全量重建）**。补齐这三块，repo-wiki 就能从一个"能用的文档生成 skill"升级为"可靠的文档生成工程"。
