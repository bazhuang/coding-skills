## 1. 结论

当前实现已经完成一批有效的基础改造，包括 Git 感知扫描、Wiki 与敏感文件排除、API 按语言分类、Spring/Feign/MQ/Job 识别、Maven/npm 模块依赖基础能力、事实层骨架、meta v2 字段骨架和 50 项自动化测试。

但本次实现尚不能认定为完成了基线方案的 P0 阶段。主要原因不是功能数量不足，而是几条关键数据链路没有闭环：

1. wiki_facts.json 已生成，但目录规划和页面生成没有真正消费事实层；
2. used_sources 已定义，但没有参与页面依赖哈希，也没有与事实 ID、Markdown 引用和 meta 做一致性验证；
3. meta v2 写出了新字段，但增量判断仍基本沿用旧的 filePaths + 内容 hash 逻辑；
4. 验证器没有拦截错误标题、越界行号、缺失符号、失效内部链接、孤儿页和 sidecar/meta 不一致；
5. 状态生命周期、扫描适配器和测试矩阵仍有明显缺口；
6. P1、P2 尚未实质实施，旧提示词中与新方案冲突的硬性要求仍然存在。

因此，本方案将后续工作分为“P0 闭环修复”“P0 完整验收”“P1 业务可用性”“P2 长期维护”四个阶段。P0 闭环修复完成前，不应把当前版本作为可信增量 Wiki 的正式发布版本。

## 4. 阻断级问题

### 4.1 Windows 下 meta.yaml 非法

证据位置：skills/repo-wiki/scripts/export_wiki.py:793-809

当前实现直接把字符串放入 YAML 双引号：

~~~yaml
repo_path: "D:\work\demo"
~~~

YAML 会把反斜杠解释为转义符，部分组合会直接导致解析失败。当前环境下已复现 unknown escape character 'w'。

整改要求：

1. 新增统一的 YAML 标量序列化函数；
2. 推荐使用 json.dumps(value, ensure_ascii=False) 生成合法的双引号标量，因为 JSON 字符串也是合法 YAML 标量；
3. 所有路径、标题、分支、符号和来源字段统一经过序列化，不允许手工拼接引号；
4. 增加 Windows 路径、双引号、冒号、换行、中文和反斜杠测试；
5. 对生成的 meta.yaml 使用独立解析器做回读验证；基础实现仍需保持标准库可运行，可在测试环境使用 PyYAML 交叉验证。

验收标准：Windows、Linux 路径及包含特殊字符的标题均能被标准 YAML 解析器正确读取。

### 4.2 事实层未接入目录和页面生成

证据位置：

- skills/repo-wiki/SKILL.md:156-175
- skills/repo-wiki/references/structure-prompt.md:1-21
- skills/repo-wiki/references/agent-contracts.yaml:17-23
- skills/repo-wiki/scripts/export_wiki.py:691-707

SKILL.md 声称目录和页面生成消费 wiki_facts.json，但结构提示词没有事实占位符，页面 Agent 的 must_read 没有事实文件，导出器读取 sidecar 时也只返回 used_sources，丢弃 facts。

整改要求：

1. 为结构提示词增加 FACTS_SUMMARY，输入经过裁剪的关键事实和冲突清单；
2. 为每个页面生成页面级事实子集，避免把完整事实层重复灌入每个 Agent；
3. page_generator.must_read 必须包含 .repo-wiki/wiki_facts.json 或页面事实子集；
4. sidecar 必须同时返回 facts 和 used_sources，缺一即页面生成失败；
5. meta 每页记录 fact_ids，并验证 ID 在事实层中存在；
6. 页面新增推断必须写入统一的 inferred facts 产物，禁止只存在于 Markdown；
7. 结构、页面和验证阶段统一使用同一份 facts schema 版本。

验收标准：任意页面的重要架构结论都能从 Markdown 定位到 sidecar，再定位到 facts 和仓库证据。

### 4.3 实际引用没有参与增量依赖

证据位置：skills/repo-wiki/scripts/export_wiki.py:581-592、733-759

当前 source_hash 只拼接结构中 filePaths 对应的内容 hash，存在以下问题：

- 文件路径不参与哈希，重命名但内容不变时无法识别；
- 缺失源文件被静默忽略；
- sidecar 中的实际来源没有参与哈希；
- 事实、提示词、Skill 版本和页面结构没有参与页面失效判断；
- facts_hash、structure_hash、prompt_hash 只是写入 meta，没有进入决策；
- 从结构中删除的页面可能继续残留。

整改要求：

页面依赖哈希至少包含：

~~~text
page_dependency_hash = hash(
  normalized_path + file_content_hash
  + actual_used_sources
  + referenced_fact_ids_and_values
  + page_structure_fragment
  + page_template_hash
  + prompt_hash
  + skill_version
)
~~~

并执行以下规则：

1. actual_used_sources 与结构规划来源取并集，实际来源优先；
2. 路径和内容同时参与哈希；
3. 任一声明来源缺失时硬失败，不得跳过；
4. 文件增加、删除、移动和内容变化必须可区分；
5. prompt 或 Skill 版本变化时，按影响范围使页面失效；
6. structure 变化时重新计算发布清单；
7. 从发布清单移除的旧页面标记为 stale，并在发布前删除或进入显式确认流程；
8. 手工编辑页面不得被静默覆盖。

验收标准：新增、删除、重命名、内容变化、事实变化、提示词变化和结构变化测试全部通过。

### 4.4 验证器不能证明产物可信

证据位置：

- skills/repo-wiki/scripts/verify_wiki.py:176-193
- skills/repo-wiki/scripts/verify_wiki.py:255-330
- skills/repo-wiki/scripts/parse_structure.py:40-99

当前验证器只检查 H1 是否存在，不检查标题一致；只检查引用文件是否存在，不检查行号和符号；内部链接和孤儿页只是软警告；没有校验 sidecar/meta；结构解析器也没有执行唯一性和引用完整性校验。

整改要求：

硬门禁必须覆盖：

1. 页面 ID、章节 ID、标题和最终输出路径唯一；
2. Windows 大小写不敏感环境下不存在路径冲突；
3. parentSection、section page_ref、subsection 和 relatedPages 全部存在；
4. 普通页面 H1 与结构标题完全一致，概览页按明确定义的例外校验；
5. 源码路径存在且 realpath 不越出仓库允许根；
6. 引用行号在文件范围内；
7. 引用符号能在文件中定位；
8. Markdown 引用、sidecar、meta 三者一致；
9. sidecar 中的事实 ID 全部存在；
10. 内部 Markdown 链接、锚点和图片存在；
11. 孤儿页、陈旧页和未登记文件阻断发布；
12. 事实冲突及通用互斥断言阻断发布；
13. 产物不含敏感路径、凭据模式和密钥内容；
14. 单次运行聚合报告全部错误，不在第一个错误处退出。

SKILL.md 的标准验证命令必须传入：

~~~bash
python3 skills/repo-wiki/scripts/verify_wiki.py \
  docs/tmp/wiki_structure.json \
  --wiki-dir docs/wiki \
  --facts .repo-wiki/wiki_facts.json \
  --repo <仓库路径> \
  [--modules docs/tmp/wiki_modules.json]
~~~

验收标准：故障注入中的错误标题、越界行号、缺失符号、失效链接、孤儿页和不一致 meta 均必须使验证返回非零退出码。

## 5. 高优先级问题

### 5.1 状态生命周期不一致

证据位置：

- skills/repo-wiki/SKILL.md:55-75、312-320
- skills/repo-wiki/references/state-ledger.md:43-53、123-143
- skills/repo-wiki/references/wiki-state.example.yaml

当前规范一处要求保留状态供下次恢复，另一处要求完成态归档或删除；步骤闭集和示例都缺少 build_facts。

整改要求：

1. 步骤闭集增加 build_facts；
2. 新运行初始化 run_id、run_status、schema 版本和仓库指纹；
3. 任一步骤失败时写入 run_status=failed；
4. 发布成功且清理完成后写入 completed_at，随后归档到 docs/.wiki-state-history/<run_id>.yaml 或删除；
5. completed 状态绝不能作为默认断点；
6. 恢复前比较 state schema、facts schema、structure schema、Skill 版本和仓库指纹；
7. 不兼容时明确迁移或重新开始。

### 5.2 Git 模式没有执行符号链接策略

证据位置：skills/repo-wiki/scripts/scan_repo.py:329-375

符号链接策略只传给目录遍历分支。Git 仓库进入 git ls-files 分支后，不会按 skip/internal-only/follow 展开链接目录。

整改要求：

1. Git 文件清单建立后，单独识别 tracked symlink；
2. 对链接目标执行 realpath、允许根、循环和重复目标检查；
3. internal-only 只允许仓库根内目标；
4. 如需读取外部需求目录，引入显式 allowed_roots 配置；
5. 扫描结果记录链接路径、目标、策略、是否展开及排除原因；
6. 增加 Git/非 Git、文件链接/目录链接、内部/外部和循环链接测试。

### 5.3 多语言模块和依赖适配器不完整

证据位置：skills/repo-wiki/scripts/scan_modules.py:435-539、982-1018

当前没有 Python package 适配器；Go 只支持 go.work 边界，Cargo/Go/Python 没有实际模块依赖计算；文档所称跨模块 import 也未实现。

整改要求：

- Python：支持 pyproject.toml、workspace/monorepo 约定、包入口和本地依赖；
- Go：支持 go.work、go.mod、module/replace 和内部 import；
- Cargo：支持 workspace members 和 path dependencies；
- Gradle：覆盖 Groovy/Kotlin DSL 常见 project(...) 写法；
- Node：继续覆盖 npm/pnpm/Lerna/Nx，并验证 workspace protocol；
- 所有适配器输出统一的 dependency evidence；
- 不支持时记录 unsupported，不能输出确定性依赖结论。

### 5.4 事实 ID 和仓库规则抽取不稳定

证据位置：skills/repo-wiki/scripts/build_facts.py:60-88、162-195

接口事实 ID 使用 file:line，代码移动会改变 ID。仓库规则目前主要抽取标题，可能漏掉正文中的真实约束；嵌套规则文件的定位也不可靠。

整改要求：

1. 接口事实 ID 优先采用类型、框架、协议、路由和稳定符号；
2. 行号只作为 evidence，不进入稳定 ID；
3. 文件重命名时通过符号和内容辅助识别；
4. 规则文件按实际匹配路径读取；
5. 抽取标题下的规则正文、列表和明确约束语句；
6. 规则仅标记为 repository_rule，不得推断实现已经遵守；
7. 冲突检测增加语义互斥断言，不只检查“同 ID 不同 value”。

## 7. P1：业务可用性优化

P0 门禁完成后，再实施基线方案中的业务可用性能力。

### 7.1 业务域模式

在全面模式和深度模式之间增加 20～40 页的业务域模式，选择依据包括模块数、部署单元、入口数、核心对象、业务能力数和源码规模，不再仅依据“是否多模块”。

### 7.2 分类页面模板

新增 references/page-templates/：

- architecture.md
- business-flow.md
- api.md
- data.md
- integration.md
- implementation.md
- operations.md

每类模板定义自己的必答问题、可选图表和证据要求。移除全局“至少 5 个源文件”和“大量使用 Mermaid”的硬性要求。

### 7.3 共享术语和规范事实

页面并行生成前输出：

- glossary.yaml
- canonical-facts.yaml
- naming-map.yaml

页面 Agent 必须读取相关子集，生成后执行跨页一致性审计。

### 7.4 业务追溯制品

输出：

- capabilities.yaml
- business-rules.yaml
- state-machines.yaml
- traceability.yaml

这些产物需要与 facts、sidecar 和 Markdown 使用同一事实 ID，不得形成第二套互不关联的数据模型。

## 8. P2：长期维护能力

### 8.1 手工内容保护

至少实现一种明确机制：生成区/人工区、overlay 或覆盖前差异确认。检测到未登记人工修改时默认禁止整页覆盖，并将处理结果写入 meta。

### 8.2 Mermaid 增强验证

基础验证保持标准库独立运行；环境允许时通过 Mermaid CLI 或等价解析器执行真实语法和渲染验证。增强验证失败可配置为发布门禁。

### 8.3 可选代码图谱适配

定义统一适配器接口，用于补充调用链、符号引用、数据关系和跨模块依赖。外部工具不可用时回退到本地扫描，并明确记录降级原因。

## 11. P0 完成定义

只有同时满足以下条件，才能把 P0 标记为完成：

- [ ] Windows 和 Linux 生成的 meta.yaml 均可被标准 YAML 解析器读取；
- [ ] 结构和页面生成真实消费统一事实层；
- [ ] 页面 Markdown、sidecar、meta 和 facts 完整一致；
- [ ] 页面依赖哈希覆盖路径、内容、实际引用、事实、结构、prompt 和 Skill 版本；
- [ ] 新增、删除、重命名和缺失源文件都能正确触发失效或硬失败；
- [ ] H1、结构引用、源码路径、行号、符号、链接、孤儿页和陈旧页均由硬门禁验证；
- [ ] 完成态不会被误恢复，状态 schema 不兼容时不会带病续跑；
- [ ] Git 和非 Git 仓库的符号链接安全边界有测试覆盖；
- [ ] Maven、Gradle、Node、Python、Go、Cargo fixtures 覆盖模块和依赖；
- [ ] 所有 P0 脚本具备直接测试及至少一条端到端链路测试；
- [ ] 在至少三类匿名化代表仓库上完成重新生成、自动验证和人工抽检；
- [ ] 生产代码、提示词和默认配置不存在样本仓库特判；
- [ ] meta、facts、state 和 structure schema 的兼容或迁移策略进入发布说明。

## 12. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 同时修改 facts、meta 和验证器导致回归面过大 | 先固定失败用例和 schema，再分提交接通链路 |
| 强门禁让旧 Wiki 无法通过 | 提供迁移报告和一次性修复工具，不降低新版本标准 |
| 页面依赖哈希过于敏感 | 区分全局输入与页面级输入，按影响范围失效 |
| 事实输入过大导致上下文膨胀 | 为结构和页面生成裁剪 facts 子集，使用稳定 ID 引用 |
| 跨语言适配器误判 | 先能力探测，再启用适配器；未知技术栈显式降级 |
| 自动清理 stale 页面误删人工文件 | 只处理发布清单登记的生成页，并在检测到人工修改时要求确认 |
| 状态迁移复杂 | 明确 schema 版本兼容矩阵，不兼容时重新开始 |

## 13. 最终目标

优化后的 repo-wiki 不只需要“生成一套结构完整的 Markdown”，还必须能够证明：

1. 输入来自干净且受控的仓库范围；
2. 关键结论来自统一事实层；
3. 每个页面的实际依赖可以被机器读取；
4. 任一源码、事实、提示词或结构变化都能正确触发影响分析；
5. 验证通过意味着路径、符号、事实、链接和发布清单真实一致；
6. Wiki 能作为新需求分析的可靠现状输入，但不会冒充正式需求或目标设计。
